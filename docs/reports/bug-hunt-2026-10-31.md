## Findings

### Schedules: backend (scheduler tick, runs, cron/time zones, notifications, API permissions)

#### A frequent cron could return no next run during the autumn overlap

- Where: `shared/src/cron.ts:156`
- Problem: `nextCronRun` retried only 8 wall minutes, and `wallToInstant` always returned the first of the two occurrences of a repeated hour. During the second pass of the autumn change (e.g. Rome 02:10 CET at 01:10Z), a five-minute cron exhausted the retries and returned `null`. Creating or resuming such a Schedule during that hour answered `400 "This cron expression never runs"`, and the scheduler could persist `nextRunAt = null`, stopping the Schedule for good with no skip row or alert.
- Spec: `docs/specs/schedules.md` ("A time that happens twice runs once, at its first occurrence"; a valid expression must keep running).
- Test: `backend/test/cron.test.ts`, "keeps a frequent expression running during the second pass of the autumn overlap"
- Fix: consider both occurrences of a repeated wall time and pick the first one after the reference instant; a gap still resolves to the first valid minute after it.

#### Global Task Tools accepted archived Projects as targets

- Where: `backend/src/mcp/server.ts:227`, `:298`, `:591`
- Problem: the global tools checked only `projects.kind === 'project'`. A global Schedule's Agent could list, read, edit, move, create, assign and start Tasks in an archived Project by key.
- Spec: `docs/specs/schedules.md` ("Only ordinary, non-archived Projects appear in the global tools' project list and accept targets").
- Test: `backend/test/schedules.test.ts`, "does not let a global Agent reach an archived Project"
- Fix: `list_tasks`, `get_task`, `update_task_by_key`, `set_task_status`, `assign_task_to_me`, `start_task` and `create_task_in_project` now reject an archived Project.

#### A low-frequency Schedule lost its last-run outcome after 1000 runs elsewhere

- Where: `backend/src/modules/schedules/service.ts:81`
- Problem: `lastRun` was picked from a single global window of the newest 1000 `schedule_runs` rows. Once the installation had more runs, a Schedule whose latest run was older than that window reported `lastRun: null`, so its row and detail showed no outcome while its own history was correct.
- Spec: `docs/specs/schedules.md` ("The list shows each Schedule with ... the outcome of the latest run").
- Test: `backend/test/schedules.test.ts`, "keeps the latest run of a low-frequency Schedule when other Schedules have thousands"
- Fix: `DISTINCT ON (schedule_id)` query for the latest run of every Schedule, with no global window.


### Schedules: web section (list, detail/form, run history, run page)

#### The run page showed a Task that is not one of the Schedule's runs

- Where: `frontend/src/pages/SchedulesPage.tsx:309`
- Problem: `ScheduleRunPage` fetched the Schedule and the Task by key independently and never checked that the Task belongs to the Schedule's Project. `/schedules/A/runs/B-task-key` rendered B's conversation under A's name and header, and an ordinary Task key did the same.
- Spec: `docs/specs/schedules.md` ("a link to the run's Task, which opens on a run page of the Schedule").
- Test: `frontend/e2e/schedules.spec.ts`, "does not show a run page for a Task of another Schedule"
- Fix: render "Run not found." when the Task's `projectId` differs from the Schedule's.

#### A closed run still offered a comment composer

- Where: `frontend/src/pages/SchedulesPage.tsx:309`, `frontend/src/components/TaskActivity.tsx:88`
- Problem: `TaskActivity` renders the `Composer` whenever `readOnly` is absent, and the run page passed nothing. A `Succeeded` or `Failed` run therefore showed "Leave a comment…", the Internal chat switch and Attach, although a closed run takes no more Comments.
- Spec: `docs/tasks/2026-10-30-scheduled-agents.md` ("A running run still takes Comments …; a closed one does not"), `docs/specs/schedules.md` ("The Timeline of a closed run stays readable").
- Test: `frontend/e2e/schedules.spec.ts`, "a finished run is read-only"
- Fix: the run page now passes a read-only notice when the Session state is `closed`.

#### A long Schedule name and long Agent names pushed the Enabled switch out of view

- Where: `frontend/src/pages/SchedulesPage.tsx:97`
- Problem: the table cells used `whitespace-nowrap` without truncation, so a 100-character name (and the timestamped Agent names) widened the table past its container. The `overflow-x-auto` wrapper did not show a scrollbar, and the Enabled switch — the only admin action of the row — sat 55 px outside the visible area at 1600 px.
- Spec: `docs/specs/schedules.md` ("The list shows each Schedule with … an enabled switch").
- Test: `frontend/e2e/schedules.spec.ts`, "a long name does not push the Enabled switch out of view"
- Fix: cap and truncate the Name, Agent and Scope cells (with `title` tooltips), so every column including Enabled fits. Screenshots: [before](bug-hunt-2026-10-31/schedules-list-before.png) · [after](bug-hunt-2026-10-31/schedules-list-after.png).

#### The create/edit dialog could not be scrolled on a short screen

- Where: `frontend/src/pages/SchedulesPage.tsx:126`, `:269`
- Problem: `DialogContent` is vertically centred with no `max-height`; the form is about 700–800 px tall. On a 1280×600 laptop the dialog overflowed the viewport and, with body scrolling locked by Radix, the title and the Create/Save button were unreachable.
- Spec: no explicit rule; the form is the only way to create a Schedule (`docs/manual/schedules.md`).
- Test: `frontend/e2e/schedules.spec.ts`, "the schedule dialog stays inside a short viewport"
- Fix: `max-h-[90dvh] overflow-y-auto` on both dialogs, as the other large dialogs already do.

#### Editing the Base Branch could silently detach a Schedule's Repository

- Where: `frontend/src/pages/SchedulesPage.tsx:337`
- Problem: the save handler rebuilt the Repository only from the repository picker's loaded list. While the listing was loading, or after its Connection failed (the group comes back empty), the selected Repository could not be resolved, so changing the Base Branch sent `repository: null` and made the Schedule global.
- Spec: `docs/specs/schedules.md` (Repository and Base Branch are part of the configuration).
- Test: `frontend/e2e/schedules.spec.ts`, "editing the Base Branch keeps the Repository when the repository list is unavailable"
- Fix: keep the stored Repository when the selected value still names it, even if the picker cannot list it.

#### The Enabled switch failed silently

- Where: `frontend/src/pages/SchedulesPage.tsx:55`
- Problem: the toggle `void`ed the PATCH without a `catch`. A failure (500, 403 after a role change, a deleted Schedule) produced an unhandled rejection in the console and no message, and the switch stayed where it was with no explanation.
- Spec: `docs/specs/clients.md` (the switch is the pause/resume control).
- Test: `frontend/e2e/schedules.spec.ts`, "a failed enabled toggle reports the error instead of failing silently"
- Fix: catch, show a toast with the server message, and disable the switch while the PATCH is in flight.

#### Double-clicking Run now started two runs

- Where: `frontend/src/pages/SchedulesPage.tsx:199`
- Problem: "Run now" and Pause/Resume had no in-flight guard. Run now deliberately ignores the previous-run check, so a double click created two Tasks for the same moment, both titled with the same timestamp.
- Spec: `docs/specs/schedules.md` ("Run now starts a run immediately … answered with the new run", singular).
- Test: `frontend/e2e/schedules.spec.ts`, "double-clicking Run now starts one run"
- Fix: a synchronous ref guard plus a busy state that disables Run now and Pause/Resume while the request runs.

#### A Schedule whose Agent was disabled could not be edited at all

- Where: `frontend/src/pages/SchedulesPage.tsx:343`
- Problem: the form always PATCHed the unchanged `agentId`; the backend re-validates any provided Agent and refuses a disabled one with `400`. Editing only the prompt or cron therefore failed, and the Agent picker showed the disabled Agent like an enabled one.
- Spec: `docs/specs/schedules.md` (the Agent must be enabled when a run starts; a disabled Agent makes runs skipped).
- Test: `frontend/e2e/schedules.spec.ts`, "a Schedule whose Agent is disabled can still be edited"
- Fix: omit `agentId` when it is unchanged, and label the current disabled Agent "(disabled)" in the picker.

#### Times are shown in the browser's zone, not the Schedule's (to confirm)

- Where: `frontend/src/pages/SchedulesPage.tsx:41`
- Behaviour: "Next run" and the run-history start time use the viewer's locale/zone, while "When" describes the cron in the Schedule's zone. A `0 9 * * *` schedule in `Europe/Rome` viewed from UTC reads "Every day at 09:00" next to "8:00 AM", with the zone only in a `title` tooltip on the When cell.
- Why it might be a bug: the two times on the same row disagree, and the manual's screenshot shows the same mismatch.
- Why it might be intended: showing instants in the reader's own zone is common, and the spec only says the cron is evaluated in the Schedule's zone.

#### The detail page does not show the Base Branch (to confirm)

- Where: `frontend/src/pages/SchedulesPage.tsx:191`
- Behaviour: the detail subtitle shows cron/time zone, Agent, `owner/name` or Global, and read-only, but not the Repository's Base Branch; non-admins cannot see it anywhere.
- Why it might be a bug: `docs/specs/schedules.md` says the detail page holds "the configuration", and Base Branch is part of it.
- Why it might be intended: the subtitle is a summary and the Branch is editable only by admins.


### Chat Dock and Minimized Chats

#### With four chats docked, the oldest title bar could never be opened

- Where: `frontend/src/lib/dock.ts:74`, `:108`
- Problem: `commit` collapsed the oldest open entries, and `toggleInDock` expanded an entry before calling it. With four entries the three newest are open and the oldest is a bar; clicking that bar removed it from `collapsed`, then the same `commit` immediately collapsed it again as the oldest open entry. The click was a visible no-op.
- Spec: `docs/specs/clients.md` ("Clicking the bar opens or collapses the panel").
- Test: `frontend/e2e/dock.spec.ts`, "opens the oldest title bar when four chats are docked"
- Fix: `commit` takes the entry being opened and never collapses it; the oldest *other* open panel makes room.

#### A docked Task's unread dot never updated away from its Board

- Where: `frontend/src/components/ChatDock.tsx:80`
- Problem: the panel subscribed to the Task topic and the Wiki topic, but a Task's unread flag comes from the Project's Task Preferences, which are refreshed by `task.updated` events published on the **Project** topic. Off the Board nothing refreshed them, so an Agent's reply never lit the Dock's unread dot.
- Spec: `docs/specs/clients.md` ("Data stays current through events and reconnection"), task user story 8.
- Test: the Project subscription is the fix; the unread event path is exercised by the Wiki Chat test below.
- Fix: the panel also subscribes to `projectTopic(task.projectId)`.

#### A Wiki Chat's unread dot stayed lit after reading it

- Where: `frontend/src/lib/cache.ts:208`, `frontend/src/components/ChatDock.tsx:100`
- Problem: a Wiki Chat's unread state lives in the Wiki's Chat list (`GET /wikis/:id/chats`). Advancing the read position emits `task.preference`, which only updated the Task Preferences cache, so the Chat list kept `unread: true`. The dot was merely hidden on the active Wiki row, and stayed visible on the Dock panel.
- Spec: `docs/specs/clients.md` ("Every client of that User updates unread and following indicators"); task user story 8 ("reading in an open panel clears the unread state everywhere").
- Test: `frontend/e2e/dock.spec.ts`, "clears a docked Wiki Chat unread dot when it is read"
- Fix: `task.preference` also patches the cached Wiki Chat lists for that Task.

#### An empty (unlisted) Wiki Chat opened a different Chat from its URL or the Dock

- Where: `frontend/src/pages/WikisPage.tsx:109`
- Problem: a New Chat reserves a Task that `GET /wikis/:id/chats` does not list until its first Comment. When the URL (or "Open full page" from the Dock) named that reserved Chat, the lookup failed and the page fell back to `list[0]`, showing another conversation while the address bar named the empty one. A Comment typed there went to the wrong Chat, and its Draft was stranded.
- Spec: `docs/specs/clients.md` ("opening one from the Dock shows its full page"), `docs/CONTEXT.md` (Draft).
- Test: `frontend/e2e/dock.spec.ts`, "does not open another Chat when the URL names an unlisted empty Chat"
- Fix: a Chat id in the URL is never replaced by another Chat; when it is not listed, the page uses its Task (it belongs to the Wiki's Project) as an empty Chat.

#### Minimizing a Wiki or Schedule Task from `/t/:key` navigated to a missing Board

- Where: `frontend/src/components/TaskDetail.tsx:353`, `:223`
- Problem: the Task page derives the Project Key from the Task Key and minimizes by navigating to `/p/<key>`. Wiki and Schedule Tasks live in hidden Projects, so the Board answers 404 and the user landed on "Project not found". The Dock entry was also stored without the Wiki identity, so its bar and the Delete Chat check lost the Wiki.
- Spec: `docs/specs/clients.md` ("a Task page returns to its Board"; a Wiki Chat is minimized from the Wiki).
- Test: `frontend/e2e/dock.spec.ts`, "offers no Minimize for a Task of a Wiki Project"
- Fix: Minimize is offered on a Task page only once the ordinary Project bundle has loaded; Wiki and Schedule Tasks are minimized from their own pages.

#### Corrupt or duplicate stored Dock entries produced stuck or doubled panels

- Where: `frontend/src/lib/dock.ts:32`
- Problem: the stored state accepted an empty `taskId` and duplicate entries. An empty id never fetches, so its panel showed a loading skeleton for ever; duplicates mounted two live copies of one conversation.
- Spec: `docs/specs/clients.md` (entries survive reloads; bad storage should degrade to the default).
- Test: `frontend/e2e/dock.spec.ts`, "drops corrupt and duplicate entries from stored Dock state"
- Fix: drop empty ids and keep the newest entry per Task.

#### Two tabs keep independent Dock copies (to confirm)

- Where: `frontend/src/lib/dock.ts:59`
- Behaviour: state is loaded once at module import and there is no `storage` listener, so a change in one tab is invisible in another and a stale tab can overwrite the stored list on its next write.
- Why it might be a bug: the Dock is described as a per-browser preference; silently losing entries is surprising.
- Why it might be intended: the theme uses the same per-tab module state, and the spec requires persistence across reloads and clearing on login/logout, not live cross-tab sync.

#### A branch created by a non-backing Wiki Chat appears after a reload (to confirm)

- Where: `frontend/src/pages/WikisPage.tsx:96`, `backend/src/sessions/dispatch.ts:81`
- Behaviour: the Wiki header reads the branch and pull request from the backing Task. `recordPullRequest` emits events on that Task, which the page now subscribes to, but the branch write in dispatch emits no event at all, so the branch link appears only after a reload.
- Why it might be a bug: `docs/specs/wikis.md` says the header shows the branch and pull request once they exist.
- Why it might be intended: the branch is created at the start of the first Job; the header's link is not otherwise live.


### Active Runs, Agent state dots and Live Turn preview

#### Tool outputs could grow a transcript past its 2 MB limit

- Where: `backend/src/sessions/runs.ts:57`
- Problem: a tool call was appended with `output: null`, so only its small input counted against `RUN_BYTES_LIMIT`. The output arrived later through `toolResult`, which cut it at 20 KB and added it without a limit check. A subagent making a few hundred calls could hold 2–10 MB per Run, against the documented 30 Runs × 2 MB bound, and nothing was marked truncated.
- Spec: `docs/specs/agent-sessions.md` (a Run holds at most 500 messages and 2 MB), `docs/tasks/2026-10-30-active-runs.md`.
- Test: `backend/test/runs.test.ts`, "keeps tool outputs inside the 2 MB transcript limit too"
- Fix: a result that would cross the limit settles the tool call without its output and marks the transcript truncated.

#### The bar was not re-sorted when a Run ended, so a failed Run jumped ahead

- Where: `frontend/src/lib/runs.ts:138`
- Problem: `useRunBar` filtered the store but kept insertion order; `upsert` replaces in place. When an older Run failed while the page was open, it stayed first even though the spec puts running Runs first, then failures.
- Spec: `docs/specs/clients.md` ("Runs that run now first, then the failed ones still to read, each in start order").
- Test: `frontend/e2e/runs.spec.ts`, "lists a running Run before an older failed one and opens it without a dialog warning"
- Fix: sort by status rank, then start time, then id.

#### The tool-call count never advanced while a Run was running

- Where: `backend/src/projection/apply.ts:97`, `backend/src/sessions/runs.ts:150`
- Problem: the registry incremented `run.toolCalls` on every tool call, but only `run.create` and `run.end` published a `run.updated`. A Task opened mid-run kept showing the count from its opening snapshot (often 0) until the Run ended.
- Spec: `docs/specs/clients.md` ("the bar shows … the tool call count"), task user story 7.
- Test: `backend/test/runs.test.ts`, "serves a running Run and its transcript…" (waits for the `run.updated` with `toolCalls: 1`)
- Fix: a tool message also publishes the Run's current summary.

#### Delete Chat left the old Runs in the store and cache

- Where: `frontend/src/lib/runs.ts:59`, `frontend/src/lib/cache.ts:173`, `frontend/src/pages/WikisPage.tsx:181`
- Problem: `timeline.reset` cleared only `runs`, leaving transcripts, the open dialog, wanted ids and dismissed ids. The cache kept the `GET /runs` snapshot, and the deleting page did not apply the event to the Run store at all. Because Delete Chat reuses the emptied Task for the next New Chat, an old failed Run could reappear in the new Chat's bar (finished runs are deliberately kept when they are no longer listed).
- Spec: `docs/specs/clients.md` (Delete Chat empties the conversation for everyone), task "a reload does not resurrect Runs that ended before it".
- Fix: reset the whole per-Task Run state, remove the cached Runs query, and apply the reset from the local Delete Chat path. The existing Delete Chat e2e covers the panel side; the Run-store reset is exercised by the same flow.

#### A discarded (Reset Chat) Job recovered without its Runs being dropped

- Where: `backend/src/runner/handlers.ts:334`
- Problem: `recoverJob` skipped `settleProjection` for a Job with `discardOutput`, and that function is the only place calling `runs.endJob`. A deleted Chat whose Runner reconnected before `job.exited` kept up to 30 Run transcripts in memory for the life of the process, still readable by Run id.
- Spec: `docs/tasks/2026-10-30-active-runs.md` ("The registry lives as long as the Job … everything goes when the Job ends").
- Fix: the recovery path now ends the Job's Runs directly when its output is discarded.

#### The Run dialog tripped Radix's missing-description warning

- Where: `frontend/src/components/ActiveRuns.tsx:126`
- Problem: `DialogContent` had a title but no `DialogDescription`, so every opening logged a development/a11y warning.
- Test: the same `frontend/e2e/runs.spec.ts` test asserts no console error mentioning a missing Description.
- Fix: an `sr-only` description naming the transcript.

#### A stale Runs snapshot can overwrite a newer `run.updated` (to confirm)

- Where: `frontend/src/lib/runs.ts:69`
- Behaviour: `setActiveRuns` upserts every entry of a `GET /runs` response over the store. If a Run ends while that request is in flight, the delayed snapshot (taken before the end) can put it back to `running`.
- Why it might be a bug: the transcript merge defends against exactly this with message numbers, and the bar would show a finished (or failed) Run again.
- Why it might be intended: the follow-up subscribe-ack refetch usually corrects it, and the race window is small.


### Task Attachments list and Composer attachments

#### A 255-character filename could cut an emoji in half and make every download 500

- Where: `backend/src/modules/comments/routes.ts:141`
- Problem: `sanitizeFilename` truncated with `slice(0, 255)`, which counts UTF-16 code units. A name whose 255th unit was the first half of an astral character (an emoji) stored a lone surrogate. `contentDisposition` then called `encodeURIComponent` on it, which throws, so every `GET /attachments/:id` for that file returned 500 although the upload succeeded and the list row rendered.
- Spec: `docs/specs/conversation.md` (names are cut to 255 characters; every attachment downloads under its name).
- Test: `backend/test/comments.test.ts`, "serves a file whose 255-character name would cut an emoji in half"
- Fix: count code points (`[...name].slice(0, 255).join('')`).

#### Pasting an image into the description never refreshed the Attachments list

- Where: `frontend/src/components/RichMarkdownEditor.tsx:346`
- Problem: the image plugin's paste/drop handler uploaded to `/tasks/:id/attachments` but did not invalidate `keys.attachments(taskId)`. The toolbar buttons did, so the list updated from them but not from a pasted or dropped image.
- Spec: `docs/specs/clients.md` ("It updates as Comments and description uploads arrive"), task acceptance 5.
- Fix: the handler now calls an `onImageUploaded` callback, and the description editor invalidates the attachment list. Covered by the same invalidation path as the toolbar uploads; the paste gesture itself is not simulated in the suite.

#### Pasting an image while editing a Comment uploaded it as a Task description file

- Where: `frontend/src/components/RichMarkdownEditor.tsx:623`
- Problem: `CommentEditor` used the same image plugin as the description editor, so an image pasted while editing a Comment was uploaded with `task_id` and `comment_id = null`: the list showed it as "Description", deleting the Comment kept it, and the next description upload's 24-hour prune could delete the blob while the Comment still linked it.
- Spec: `docs/specs/conversation.md` (a Comment carries its own Attachments; description files are pruned when no longer linked).
- Fix: the comment editor no longer includes the image-upload plugin; images belong to the Comment being written in the Composer.

#### A description upload from another page was invisible until reload

- Where: `backend/src/modules/comments/routes.ts:41`, `frontend/src/lib/cache.ts:204`
- Problem: `POST /tasks/:id/attachments` published no event, and only the initiating component invalidated its own list. Another tab or User with the Task open kept the old list (and a file pruned by another upload stayed listed, then 404ed).
- Spec: `docs/specs/clients.md` ("It updates as Comments and description uploads arrive").
- Test: `frontend/e2e/attachments.spec.ts`, "shows a description file uploaded from another page without reloading"
- Fix: the upload emits the Task's change event after commit, and `task.changed` invalidates the attachment list.

#### The description upload route let non-board Tasks accept files

- Where: `backend/src/modules/comments/routes.ts:41`
- Problem: unlike every other description-mutating route, it did not call `assertBoardTask`, so a Wiki Chat or Scheduled Run Task accepted description-attachment uploads while `PATCH /tasks/:id` answered 403 for it. The files were orphaned (no description editor) and counted toward the limit.
- Spec: Wiki and Schedule Tasks are managed through their own APIs.
- Test: `backend/test/schedules.test.ts`, "refuses people editing, moving or deleting the Task of a run" now also uploads a description file and expects 403.
- Fix: call `assertBoardTask` before receiving the files.

#### A send that completes after the composer unmounts can leave a duplicate Draft (to confirm)

- Where: `frontend/src/components/Composer.tsx:101`, `frontend/src/lib/drafts.ts:9`
- Behaviour: the sent body/files are cleared through component state and the editor, which are no-ops after unmount; the module-level Draft map keeps them, so reopening the Task shows the sent comment as unsent and Send posts it twice.
- Why it might be a bug: a Draft is by definition unsent, and only the sent text should leave the composer.
- Why it might be intended: the window needs a navigation or close while a large upload is in flight, and no test covers it.


### Projects list, Project sidebar summary and Project Skills in the composer

#### A failed Projects request looked like an empty installation

- Where: `frontend/src/pages/ProjectsPage.tsx:54`, `frontend/src/components/Layout.tsx:100`
- Problem: `useProjects()` had no error branch. On an initial failure `isPending` is false and `data` is undefined, so the grid fell through to the empty `<ul>` and the page looked like a user with no Projects; the sidebar simply dropped the Boards section. No message, no Retry. Every sibling list page renders `ErrorText`.
- Test: `frontend/e2e/robustness.spec.ts`, "shows a Projects error instead of an empty list"
- Fix: render the error and a Retry button when the list failed with no data.

#### A `/command` inside a list, heading or quote was offered as a Native Command (open)

- Where: `frontend/src/components/RichMarkdownEditor.tsx:570`
- Behaviour: `atStart` comes from the Lexical structure (`command.start === 0`, first top-level element), not from the Markdown that is sent. A first line like `- /compact`, `# /compact` or `> /compact` passes the check, so the composer offers every Claude/MCP command, but the backend requires the body to start with `/` and delivers it as text.
- Why it might be a bug: the flag is meant to match the backend's body-start rule, and the command never runs.
- Why it might be intended: the check is about where the caret is, and the backend remains the authority; no test covers it.

#### `board.md` still describes the old Project-card summary (needs a spec decision)

- Where: `docs/specs/board.md:56`
- Behaviour: it says the card shows total Tasks, the share done including `closed`, a bar split by every Category and a count per Category. The code, `docs/specs/clients.md` and the sidebar task show open/review/done with backlog and active counted as open and closed left out.
- Why it matters: the implementation follows `clients.md`; this is a stale spec sentence, not a code defect. **This needs a decision on which spec is authoritative before editing either.**
- Fixing the docs only would not change behaviour, but the instructions for this hunt say not to change what the specs state without asking.

#### An all-closed Project has no sidebar summary (to confirm)

- Where: `frontend/src/components/ProjectNavItem.tsx:62`
- Behaviour: the bar and `open/total` render only when `open + review + done > 0`; a Project whose Tasks are all in `closed` Statuses looks exactly like a Project with no Tasks, while the Projects card says "All tasks closed".
- Why it might be a bug: the clients spec says "A Project with Tasks also shows …".
- Why it might be intended: the bar deliberately excludes closed Tasks, and a zero-length bar would say nothing.


### Wiki Chats

#### Reading a Wiki Chat never cleared its unread state

- Where: `frontend/src/lib/cache.ts:208`
- Problem: a Chat's unread flag lives in its Wiki's Chat list, and advancing the read position emitted only `task.preference`, which updated the Task Preferences cache. The Chat list kept `unread: true`; the dot was hidden only on the active Wiki row and stayed lit on the Dock panel.
- Spec: `docs/specs/clients.md` ("Every client of that User updates unread and following indicators").
- Test: `frontend/e2e/dock.spec.ts`, "clears a docked Wiki Chat unread dot when it is read"
- Fix: `task.preference` patches the cached Wiki Chat lists (see the Chat Dock section).

#### An unlisted empty Chat could not be reopened by URL or from the Dock

- Where: `frontend/src/pages/WikisPage.tsx:109`
- Problem: a New Chat is not listed until its first Comment; when its URL was opened, the page fell back to `list[0]` and showed a different conversation.
- Test: `frontend/e2e/dock.spec.ts`, "does not open another Chat when the URL names an unlisted empty Chat"
- Fix: a Chat id in the URL is resolved from its Task when it is not yet listed (see the Chat Dock section).

#### The Wiki header's branch link did not update when another Chat created it (to confirm)

- Where: `frontend/src/pages/WikisPage.tsx:96`, `backend/src/sessions/dispatch.ts:81`
- Behaviour: the page now subscribes to the backing Task, which fixes pull-request updates (`task.changed` reaches it). The branch written by dispatch on the backing Task emits no event, so its link appears after a reload.
- Why it might be a bug: `docs/specs/wikis.md` says the header shows the branch once it exists.
- Why it might be intended: the branch is written at the first Job's start, and the header is informational until then.

#### Changing the Wiki's Agent away and back can drop queued Comments (to confirm)

- Where: `backend/src/sessions/lifecycle.ts:142`, `:166`
- Behaviour: a queued Comment is removed with `agent unassigned` when the Wiki switches Agent, and `resumeTaskSession` only flips the state; unlike `reassign`, it does not re-enqueue the Comments marked undelivered. The next Comment starts a Job carrying only itself.
- Why it might be a bug: `docs/specs/wikis.md` says the Chats continue where they stopped, and the ordinary return-to-Agent path explicitly re-queues those Comments.
- Why it might be intended: the delivery table says `agent unassigned` means the Agent will never receive it.

#### Deleting an Agent leaves an open Wiki page's Chat list stale (to confirm)

- Where: `backend/src/modules/tasks/service.ts:550`, `frontend/src/pages/WikisPage.tsx:194`
- Behaviour: deleting an Agent that ran older Chats clears `agentId` on their Tasks but emits no `wiki.changed`, so an already-open Wiki page keeps showing "This chat is run by another agent" and hides the composer until a reload; the backend would accept the next Comment and reassign the Chat.
- Why it might be intended: it only affects pages open at deletion time, and a reload repairs them.


### Voice Rooms

#### A lone invalid TURN port or lifetime was silently ignored

- Where: `backend/src/config.ts:88`
- Problem: TURN counted as enabled only when `VOICE_TURN_HOST`, `VOICE_TURN_SECRET` or `VOICE_TURN_TLS_PORT` was set. A deployment that set only `VOICE_TURN_PORT=abc` or `VOICE_TURN_TTL_SECONDS=299` started with TURN off instead of failing at startup; `VOICE_TURN_TLS_PORT` alone did fail, so the behaviour was inconsistent.
- Spec: `docs/specs/voice-rooms.md` (partial settings and invalid ports fail at startup).
- Test: `backend/test/voice-turn-config.test.ts`, "rejects a lone TURN port or lifetime as a partial configuration"
- Fix: any `VOICE_TURN_*` variable enables the validation block.

#### The Voice controller can carry a stale error into the next Login (open)

- Where: `frontend/src/lib/voice.ts:91`
- Behaviour: `join()`'s `catch` writes `state.error` without the epoch guard its `finally` uses. A logout or a `reset()` while a join is awaiting `voice.joined` clears the error, then the rejected promise's catch re-sets it, and the module singleton shows it after the next Login. It can also overwrite a more actionable `leave()` error.
- Why it might be a bug: `reset()` exists precisely to prevent this, and the native side guards the equivalent write.

#### Native Android notification names the rejected Task after a failed transfer (open)

- Where: `mobile-app/lib/src/voice.dart:86`
- Behaviour: the foreground service is re-targeted to the requested Task before admission; a failed transfer leaves the ongoing notification pointing at the new Task while the audio session is still the old room.
- Why it might be a bug: the persistent control should name the room actually joined.

#### Native voice panel can show "Room unavailable" for the wrong Task (open)

- Where: `mobile-app/lib/src/voice_widgets.dart:61`
- Behaviour: the success path guards against a stale response, the `catch` only checks `mounted`; a failed snapshot for a previous Task can set the error on the current Task.

#### The Join button is disabled while the room snapshot is pending (open)

- Where: `frontend/src/components/VoiceRoom.tsx:37`
- Behaviour: joining is a WebSocket command independent of the snapshot, but `room.isPending` disables the button and the API client has no timeout, so a stalled snapshot keeps Join disabled indefinitely.
- Why it might be a bug: the code's own comment says a failed snapshot must not lock the button.

#### A microphone that ends during the join handshake is admitted silently (open)

- Where: `frontend/src/lib/voice.ts:70`
- Behaviour: the track's `onended` is attached only after admission, and there is no `readyState` check; a track that ends while waiting for `voice.joined` leaves the User looking connected but transmitting nothing. The native client never subscribes to track-ended at all.
- Why it might be a bug: the spec promises actionable capture errors.
- Verifying device-removal timing needs a manual run.


### Cross-cutting visual robustness on Board and Task detail

#### A failed Timeline refetch replaced the whole conversation with an error

- Where: `frontend/src/components/Timeline.tsx:45`
- Problem: `if (timeline.error) return <ErrorText>` ran even when pages were already loaded. A failed reconnect refetch or `timeline.reset` refetch replaced every Comment, Revision and Agent item with one error line, with no retry.
- Spec: `docs/specs/clients.md` ("Data stays current through events and reconnection"; the Task view keeps its loaded pages).
- Test: `frontend/e2e/robustness.spec.ts`, "keeps the loaded Timeline when its refetch fails"
- Fix: only an initial-load error takes the whole view (`isLoadingError`); with data, an inline error with "Try again" sits above the kept Timeline.

#### A Task page never kept its Statuses and Tags current

- Where: `frontend/src/components/TaskDetail.tsx:56`
- Problem: `statuses` and `tags` come from the Project bundle, but only `BoardPage` subscribed to the Project topic. Opened at `/t/:key`, renaming, recolouring, reordering or adding a Status or Tag never reached the open Task; a moved Task could show a blank Status select.
- Spec: `docs/specs/clients.md` (the Project topic carries the whole Status and Tag lists; changes appear in other open clients).
- Test: `frontend/e2e/robustness.spec.ts`, "picks up a Status renamed while the Task page is open"
- Fix: the Task view subscribes to `projectTopic(task.projectId)`.

#### Quick add created duplicate Tasks on a repeated or held Enter

- Where: `frontend/src/pages/BoardPage.tsx:335`
- Problem: `submit` had no in-flight guard and cleared the title only after the response, so a second Enter (or key repeat) on a slow request posted the same title again and created a second Task.
- Spec: `docs/specs/board.md` ("Enter creates the Task … and keeps the field open for the next one", one Task per title).
- Test: `frontend/e2e/robustness.spec.ts`, "a rapid double Enter in Quick add creates one Task"
- Fix: a busy guard plus clearing the field immediately; the title comes back if creating it fails.

#### Board query failures looked like an empty Board or a missing Project

- Where: `frontend/src/pages/BoardPage.tsx:78`, `:110`
- Problem: any `useProject` failure (not only 404) rendered "Project not found"; a failed task list fell through to `tasks.data ?? []` and showed every column empty with working Add buttons, indistinguishable from lost work.
- Spec: `docs/specs/clients.md` (server and network failures are reported as such).
- Test: `frontend/e2e/robustness.spec.ts`, "shows a Board error instead of an empty Board"
- Fix: only a 404 renders NotFound; other bundle failures render the error. A failing initial task list renders the error instead of an empty Board.

#### Copy link failed silently outside a secure context

- Where: `frontend/src/components/TaskDetail.tsx:218`
- Problem: `navigator.clipboard.writeText` was awaited without a catch. Over plain HTTP (where `navigator.clipboard` is undefined) or when permission is denied, the click produced an unhandled rejection and no feedback.
- Test: `frontend/e2e/robustness.spec.ts`, "reports a Copy link failure instead of failing silently"
- Fix: catch and show an error toast.

#### An Agent avatar whose image failed showed a broken image

- Where: `frontend/src/components/agents.tsx:15`
- Problem: `AgentAvatar` rendered the `<img>` with no `onError`, while its emoji and colour were only applied when no URL was set. A deleted or failing avatar blob left a blank/broken box.
- Fix: on image error, fall back to the emoji on its colour, like `UserAvatar` and `ProjectLogo`. (Verified by inspection; the avatar upload test adds no 404 case.)

#### These findings were left open in this pass

- **Timeline events vs. an in-flight snapshot** (`frontend/src/lib/cache.ts:133`): `putTimelineItem` neither cancels nor merges with a fetch already in flight, so a Comment can be dropped or an older page can overwrite it. The Board/Build/Job lists already defend against this; the Timeline does not. Reproducing it deterministically needs a held response, and the fix should copy `updateCachedList`'s reconciliation. **To confirm and fix next pass.**
- **Keyboard opening of Board cards** (`frontend/src/pages/BoardPage.tsx:394`): dnd-kit uses Enter/Space to start a keyboard drag, and only `article onClick` opens the Task, so a keyboard user cannot open a card and focus has no ring. This needs a product decision: a separate Open action, or a different drag key.
- **Save failures other than 409** (`frontend/src/components/TaskDetail.tsx:116`): a network/500 failure is treated like a conflict by the Description (false "Someone else changed…" banner) and discards a typed Title. The fix must distinguish error kinds; the 409 path is the one the specs describe.
- **Long unbroken titles, Tag names and filenames** (`frontend/src/pages/BoardPage.tsx:487`, `common.tsx:85`, `Timeline.tsx:359`, `Composer.tsx:210`): no `break-words`/`truncate`, so a 200-character URL-like title or a long tag adds a horizontal scrollbar to a column. A CSS fix, but the exact truncation policy is a design choice.
- **Light-theme contrast** (`agents.tsx:85`, `BoardPage.tsx:496`, `TaskDetail.tsx:759`, `Timeline.tsx:182`, `common.tsx:71`): the 400-level Tailwind accents on tinted backgrounds measure ~2:1 in Light mode for 11–12 px text. Needs light/dark token pairs, a design change.
- **Internal chat choice alone is not kept as a Draft** (`frontend/src/components/Composer.tsx:28`): an empty draft with the Internal switch on is not stored, although the manual says the choice survives reopening.
- **Read-position retry** (`frontend/src/components/TaskActivity.tsx:104`): `sent.current` is set before the PUT resolves, so after a failed report a later scroll with the same newest id does not retry, contrary to the code comment.
