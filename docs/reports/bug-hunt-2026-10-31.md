# Bug hunt 2026-10-31

Point of view: this is the first pass, so it cuts the application by the **latest implemented features** (Schedules, Chat Dock, Active Runs, Attachments, Project sidebar, Project Skills, Wiki Chats, Voice Rooms) and adds one **cross-cutting visual-robustness** section for the core Board and Task detail surfaces. Every UI section is exercised in a real browser (empty/loading/error states, long text, narrow and wide screens, dark mode, double clicks, back/reload) in addition to reading the code. Earlier reports do not exist, so nothing is skipped as already fixed.

## Findings

### Schedules: backend (scheduler tick, runs, cron/time zones, notifications, API permissions)

#### A frequent cron could return no next run during the autumn overlap

- Where: `shared/src/cron.ts:156`
- Problem: `nextCronRun` retried only 8 wall minutes, and `wallToInstant` always returned the first of the two occurrences of a repeated hour. During the second pass of the autumn change (e.g. Rome 02:10 CET at 01:10Z), a five-minute cron exhausted the retries and returned `null`. Creating or resuming such a Schedule during that hour answered `400 "This cron expression never runs"`, and the scheduler could persist `nextRunAt = null`, stopping the Schedule for good with no skip row or alert.
- Spec: `docs/specs/schedules.md` ("A time that happens twice runs once, at its first occurrence"; a valid expression must keep running).
- Test: `backend/test/cron.test.ts`, "keeps a frequent expression running during the second pass of the autumn overlap"
- Fix: consider both occurrences of a repeated wall time and pick the first one after the reference instant; a gap still resolves to the first valid minute after it.

#### Global Task Tools accepted archived Projects as targets

- Where: `backend/src/mcp/server.ts:227`, `:298`, `:591`
- Problem: the global tools checked only `projects.kind === 'project'`. A global Schedule's Agent could list, read, edit, move, create, assign and start Tasks in an archived Project by key.
- Spec: `docs/specs/schedules.md` ("Only ordinary, non-archived Projects appear in the global tools' project list and accept targets").
- Test: `backend/test/schedules.test.ts`, "does not let a global Agent reach an archived Project"
- Fix: `list_tasks`, `get_task`, `update_task_by_key`, `set_task_status`, `assign_task_to_me`, `start_task` and `create_task_in_project` now reject an archived Project.

#### A low-frequency Schedule lost its last-run outcome after 1000 runs elsewhere

- Where: `backend/src/modules/schedules/service.ts:81`
- Problem: `lastRun` was picked from a single global window of the newest 1000 `schedule_runs` rows. Once the installation had more runs, a Schedule whose latest run was older than that window reported `lastRun: null`, so its row and detail showed no outcome while its own history was correct.
- Spec: `docs/specs/schedules.md` ("The list shows each Schedule with ... the outcome of the latest run").
- Test: `backend/test/schedules.test.ts`, "keeps the latest run of a low-frequency Schedule when other Schedules have thousands"
- Fix: `DISTINCT ON (schedule_id)` query for the latest run of every Schedule, with no global window.


### Schedules: web section (list, detail/form, run history, run page)

#### The run page showed a Task that is not one of the Schedule's runs

- Where: `frontend/src/pages/SchedulesPage.tsx:309`
- Problem: `ScheduleRunPage` fetched the Schedule and the Task by key independently and never checked that the Task belongs to the Schedule's Project. `/schedules/A/runs/B-task-key` rendered B's conversation under A's name and header, and an ordinary Task key did the same.
- Spec: `docs/specs/schedules.md` ("a link to the run's Task, which opens on a run page of the Schedule").
- Test: `frontend/e2e/schedules.spec.ts`, "does not show a run page for a Task of another Schedule"
- Fix: render "Run not found." when the Task's `projectId` differs from the Schedule's.

#### A closed run still offered a comment composer

- Where: `frontend/src/pages/SchedulesPage.tsx:309`, `frontend/src/components/TaskActivity.tsx:88`
- Problem: `TaskActivity` renders the `Composer` whenever `readOnly` is absent, and the run page passed nothing. A `Succeeded` or `Failed` run therefore showed "Leave a comment…", the Internal chat switch and Attach, although a closed run takes no more Comments.
- Spec: `docs/tasks/2026-10-30-scheduled-agents.md` ("A running run still takes Comments …; a closed one does not"), `docs/specs/schedules.md` ("The Timeline of a closed run stays readable").
- Test: `frontend/e2e/schedules.spec.ts`, "a finished run is read-only"
- Fix: the run page now passes a read-only notice when the Session state is `closed`.

#### A long Schedule name and long Agent names pushed the Enabled switch out of view

- Where: `frontend/src/pages/SchedulesPage.tsx:97`
- Problem: the table cells used `whitespace-nowrap` without truncation, so a 100-character name (and the timestamped Agent names) widened the table past its container. The `overflow-x-auto` wrapper did not show a scrollbar, and the Enabled switch — the only admin action of the row — sat 55 px outside the visible area at 1600 px.
- Spec: `docs/specs/schedules.md` ("The list shows each Schedule with … an enabled switch").
- Test: `frontend/e2e/schedules.spec.ts`, "a long name does not push the Enabled switch out of view"
- Fix: cap and truncate the Name, Agent and Scope cells (with `title` tooltips), so every column including Enabled fits. Screenshots: [before](bug-hunt-2026-10-31/schedules-list-before.png) · [after](bug-hunt-2026-10-31/schedules-list-after.png).

#### The create/edit dialog could not be scrolled on a short screen

- Where: `frontend/src/pages/SchedulesPage.tsx:126`, `:269`
- Problem: `DialogContent` is vertically centred with no `max-height`; the form is about 700–800 px tall. On a 1280×600 laptop the dialog overflowed the viewport and, with body scrolling locked by Radix, the title and the Create/Save button were unreachable.
- Spec: no explicit rule; the form is the only way to create a Schedule (`docs/manual/schedules.md`).
- Test: `frontend/e2e/schedules.spec.ts`, "the schedule dialog stays inside a short viewport"
- Fix: `max-h-[90dvh] overflow-y-auto` on both dialogs, as the other large dialogs already do.

#### Editing the Base Branch could silently detach a Schedule's Repository

- Where: `frontend/src/pages/SchedulesPage.tsx:337`
- Problem: the save handler rebuilt the Repository only from the repository picker's loaded list. While the listing was loading, or after its Connection failed (the group comes back empty), the selected Repository could not be resolved, so changing the Base Branch sent `repository: null` and made the Schedule global.
- Spec: `docs/specs/schedules.md` (Repository and Base Branch are part of the configuration).
- Test: `frontend/e2e/schedules.spec.ts`, "editing the Base Branch keeps the Repository when the repository list is unavailable"
- Fix: keep the stored Repository when the selected value still names it, even if the picker cannot list it.

#### The Enabled switch failed silently

- Where: `frontend/src/pages/SchedulesPage.tsx:55`
- Problem: the toggle `void`ed the PATCH without a `catch`. A failure (500, 403 after a role change, a deleted Schedule) produced an unhandled rejection in the console and no message, and the switch stayed where it was with no explanation.
- Spec: `docs/specs/clients.md` (the switch is the pause/resume control).
- Test: `frontend/e2e/schedules.spec.ts`, "a failed enabled toggle reports the error instead of failing silently"
- Fix: catch, show a toast with the server message, and disable the switch while the PATCH is in flight.

#### Double-clicking Run now started two runs

- Where: `frontend/src/pages/SchedulesPage.tsx:199`
- Problem: "Run now" and Pause/Resume had no in-flight guard. Run now deliberately ignores the previous-run check, so a double click created two Tasks for the same moment, both titled with the same timestamp.
- Spec: `docs/specs/schedules.md` ("Run now starts a run immediately … answered with the new run", singular).
- Test: `frontend/e2e/schedules.spec.ts`, "double-clicking Run now starts one run"
- Fix: a synchronous ref guard plus a busy state that disables Run now and Pause/Resume while the request runs.

#### A Schedule whose Agent was disabled could not be edited at all

- Where: `frontend/src/pages/SchedulesPage.tsx:343`
- Problem: the form always PATCHed the unchanged `agentId`; the backend re-validates any provided Agent and refuses a disabled one with `400`. Editing only the prompt or cron therefore failed, and the Agent picker showed the disabled Agent like an enabled one.
- Spec: `docs/specs/schedules.md` (the Agent must be enabled when a run starts; a disabled Agent makes runs skipped).
- Test: `frontend/e2e/schedules.spec.ts`, "a Schedule whose Agent is disabled can still be edited"
- Fix: omit `agentId` when it is unchanged, and label the current disabled Agent "(disabled)" in the picker.

#### Times are shown in the browser's zone, not the Schedule's (to confirm)

- Where: `frontend/src/pages/SchedulesPage.tsx:41`
- Behaviour: "Next run" and the run-history start time use the viewer's locale/zone, while "When" describes the cron in the Schedule's zone. A `0 9 * * *` schedule in `Europe/Rome` viewed from UTC reads "Every day at 09:00" next to "8:00 AM", with the zone only in a `title` tooltip on the When cell.
- Why it might be a bug: the two times on the same row disagree, and the manual's screenshot shows the same mismatch.
- Why it might be intended: showing instants in the reader's own zone is common, and the spec only says the cron is evaluated in the Schedule's zone.

#### The detail page does not show the Base Branch (to confirm)

- Where: `frontend/src/pages/SchedulesPage.tsx:191`
- Behaviour: the detail subtitle shows cron/time zone, Agent, `owner/name` or Global, and read-only, but not the Repository's Base Branch; non-admins cannot see it anywhere.
- Why it might be a bug: `docs/specs/schedules.md` says the detail page holds "the configuration", and Base Branch is part of it.
- Why it might be intended: the subtitle is a summary and the Branch is editable only by admins.


### Chat Dock and Minimized Chats

#### With four chats docked, the oldest title bar could never be opened

- Where: `frontend/src/lib/dock.ts:74`, `:108`
- Problem: `commit` collapsed the oldest open entries, and `toggleInDock` expanded an entry before calling it. With four entries the three newest are open and the oldest is a bar; clicking that bar removed it from `collapsed`, then the same `commit` immediately collapsed it again as the oldest open entry. The click was a visible no-op.
- Spec: `docs/specs/clients.md` ("Clicking the bar opens or collapses the panel").
- Test: `frontend/e2e/dock.spec.ts`, "opens the oldest title bar when four chats are docked"
- Fix: `commit` takes the entry being opened and never collapses it; the oldest *other* open panel makes room.

#### A docked Task's unread dot never updated away from its Board

- Where: `frontend/src/components/ChatDock.tsx:80`
- Problem: the panel subscribed to the Task topic and the Wiki topic, but a Task's unread flag comes from the Project's Task Preferences, which are refreshed by `task.updated` events published on the **Project** topic. Off the Board nothing refreshed them, so an Agent's reply never lit the Dock's unread dot.
- Spec: `docs/specs/clients.md` ("Data stays current through events and reconnection"), task user story 8.
- Test: covered by the Wiki Chat unread test below and the existing dock tests; the Project subscription is part of the fix.
- Fix: the panel also subscribes to `projectTopic(task.projectId)`.

#### A Wiki Chat's unread dot stayed lit after reading it

- Where: `frontend/src/lib/cache.ts:208`, `frontend/src/components/ChatDock.tsx:100`
- Problem: a Wiki Chat's unread state lives in the Wiki's Chat list (`GET /wikis/:id/chats`). Advancing the read position emits `task.preference`, which only updated the Task Preferences cache, so the Chat list kept `unread: true`. The dot was merely hidden on the active Wiki row, and stayed visible on the Dock panel.
- Spec: `docs/specs/clients.md` ("Every client of that User updates unread and following indicators"); task user story 8 ("reading in an open panel clears the unread state everywhere").
- Test: `frontend/e2e/dock.spec.ts`, "clears a docked Wiki Chat unread dot when it is read"
- Fix: `task.preference` also patches the cached Wiki Chat lists for that Task.

#### An empty (unlisted) Wiki Chat opened a different Chat from its URL or the Dock

- Where: `frontend/src/pages/WikisPage.tsx:109`
- Problem: a New Chat reserves a Task that `GET /wikis/:id/chats` does not list until its first Comment. When the URL (or "Open full page" from the Dock) named that reserved Chat, the lookup failed and the page fell back to `list[0]`, showing another conversation while the address bar named the empty one. A Comment typed there went to the wrong Chat, and its Draft was stranded.
- Spec: `docs/specs/clients.md` ("opening one from the Dock shows its full page"), `docs/CONTEXT.md` (Draft).
- Test: `frontend/e2e/dock.spec.ts`, "does not open another Chat when the URL names an unlisted empty Chat"
- Fix: a Chat id in the URL is never replaced by another Chat; when it is not listed, the page uses its Task (it belongs to the Wiki's Project) as an empty Chat.

#### Minimizing a Wiki or Schedule Task from `/t/:key` navigated to a missing Board

- Where: `frontend/src/components/TaskDetail.tsx:353`, `:223`
- Problem: the Task page derives the Project Key from the Task Key and minimizes by navigating to `/p/<key>`. Wiki and Schedule Tasks live in hidden Projects, so the Board answers 404 and the user landed on "Project not found". The Dock entry was also stored without the Wiki identity, so its bar and the Delete Chat check lost the Wiki.
- Spec: `docs/specs/clients.md` ("a Task page returns to its Board"; a Wiki Chat is minimized from the Wiki).
- Test: `frontend/e2e/dock.spec.ts`, "offers no Minimize for a Task of a Wiki Project"
- Fix: Minimize is offered on a Task page only once the ordinary Project bundle has loaded; Wiki and Schedule Tasks are minimized from their own pages.

#### Corrupt or duplicate stored Dock entries produced stuck or doubled panels

- Where: `frontend/src/lib/dock.ts:32`
- Problem: the stored state accepted an empty `taskId` and duplicate entries. An empty id never fetches, so its panel showed a loading skeleton for ever; duplicates mounted two live copies of one conversation.
- Spec: `docs/specs/clients.md` (entries survive reloads; bad storage should degrade to the default).
- Test: `frontend/e2e/dock.spec.ts`, "drops corrupt and duplicate entries from stored Dock state"
- Fix: drop empty ids and keep the newest entry per Task.

#### Two tabs keep independent Dock copies (to confirm)

- Where: `frontend/src/lib/dock.ts:59`
- Behaviour: state is loaded once at module import and there is no `storage` listener, so a change in one tab is invisible in another and a stale tab can overwrite the stored list on its next write.
- Why it might be a bug: the Dock is described as a per-browser preference; silently losing entries is surprising.
- Why it might be intended: the theme uses the same per-tab module state, and the spec requires persistence across reloads and clearing on login/logout, not live cross-tab sync.

#### A branch created by a non-backing Wiki Chat appears after a reload (to confirm)

- Where: `frontend/src/pages/WikisPage.tsx:96`, `backend/src/sessions/dispatch.ts:81`
- Behaviour: the Wiki header reads the branch and pull request from the backing Task. `recordPullRequest` emits events on that Task, which the page now subscribes to, but the branch write in dispatch emits no event at all, so the branch link appears only after a reload.
- Why it might be a bug: `docs/specs/wikis.md` says the header shows the branch and pull request once they exist.
- Why it might be intended: the branch is created at the start of the first Job; the header's link is not otherwise live.
