# Bug hunt 2026-11-03

Point of view: the previous pass (2026-10-31) cut the application by its latest features. This pass follows the recurring production symptom instead: **Workers that wedge, and Tasks that wait in a Worker's Queue while the Worker looks free**, until someone restarts the Agent containers. The sections therefore cut the Worker execution path by layer and by failure mode (Queue and dispatch, Runner connection and recovery, reconciliation and autoscaling, the Job lifecycle around a container, the Runner process and entrypoint, builds and upgrades, Worker actions and Queue management, the Workers UI, and the persistence/concurrency invariants underneath). The previous report fixed no Worker-specific finding, so nothing is skipped as already fixed.

## Findings

### Queue and dispatch pipeline

#### A Comment posted while a Project moved could be queued on the old Worker

- Where: `backend/src/sessions/lifecycle.ts:39`
- Problem: `lockTaskWorker` read `projects.worker_id` before waiting for the old Worker's row lock. A concurrent Project move holds the Project update and the old Worker lock; the Comment read the old Worker, waited, then enqueued after the move committed. The Task could run on a Worker the Project no longer uses, on the old Worker Volume, and the new Worker never saw its Queue Entry.
- Spec: `docs/specs/workers.md` ("The Project's Queue Entries move to the new Worker's Queue in the same transaction", "Every Project runs on exactly one Worker").
- Test: `backend/test/workers.test.ts`, "queues a Comment on the new Worker when the Project moves at the same time".
- Fix: `lockTaskWorker` now share-locks the Project row before reading its Worker, so it serializes with `changeProjectWorker` and reads the committed value.

### Runner connection, hello/reconnect and abandoned-Job recovery

#### A Job whose Runner connection was lost with the backend was never recovered

- Where: `backend/src/runner/handlers.ts:475`, `backend/src/server.ts:92`
- Problem: `recoverAbandonedJobs` only considered Jobs whose `worker_containers.runner_disconnected_at` was older than the timeout. After a backend restart, the new process never receives the old sockets' close events, so the column kept `NULL` from the last `hello`; the Job stayed active forever and its container stayed busy.
- Spec: `docs/specs/runner.md` ("The backend also recovers a Job as interrupted when the Runner stays disconnected for more than 5 minutes"), `docs/specs/workers.md` (Runner connection).
- Test: `backend/test/workers.test.ts`, "recovers a Job whose Runner connection was lost with the backend".
- Fix: at startup every Runner connection is marked lost (`markRunnerConnectionsLost`), and recreated/restarted containers get a fresh disconnect timestamp until their `hello` clears it.

#### A failed Runner message was logged and never resent

- Where: `backend/src/runner/hub.ts:69`
- Problem: the per-connection message chain caught a handler error, logged it and continued. The message's seq stayed unacknowledged in the Runner's outbox, but a live socket never resends it: a transient database failure while handling `job.exited` left the Job active forever, and a failed `hello` left the container connected yet never ready.
- Spec: `docs/specs/runner.md` (Delivery: seq, ack and resend; "No lost output").
- Test: `backend/test/sessions.test.ts`, "reconnects a Runner whose Job message the backend could not process".
- Fix: a failed handler now drops the Runner connection, so the Runner reconnects and resends its unacknowledged messages (already-processed seqs stay ignored).

#### A free container whose Runner never reconnected kept the Queue waiting forever

- Where: `backend/src/agents/scheduler.ts:348` (`runnerGone`), `backend/src/agents/scheduler.ts:464`
- Problem: the reconciler counted a running container as available and a wanted slot, even when its Runner had been gone longer than the reconnect timeout. With a minimum of 1, the idle stop never applied, so the Worker showed a free container and its Queue never dispatched until an Admin restarted the container by hand.
- Spec: `docs/specs/workers.md` (Dispatch readiness; Worker Containers and the reconciler), `docs/specs/runner.md` (reconnect timeout).
- Test: `backend/test/workers.test.ts`, "recreates a free container whose Runner stays away, so its queued work resumes".
- Fix: a wanted, free, running container with no ready Runner past `runnerReconnectTimeoutMs` is recreated; the Worker Volume and Service Volume are kept. Recreated and restarted containers get a fresh disconnect timestamp.

### Worker Container reconciliation, autoscaling, stop and recreate

#### Disabling a Worker with `WORKER_STOP_WHEN_UNUSED=false` left its containers running forever

- Where: `backend/src/agents/scheduler.ts:411`
- Problem: `wantedSlots` added every up container when the idle stop was off, then returned early for a disabled Worker. The disabled Worker therefore kept all its containers (minimum included), although the spec says they stop once idle for `WORKER_IDLE_MINUTES`.
- Spec: `docs/specs/workers.md` ("A disabled Worker starts no slot: its running Worker Containers stop once each has been idle for `WORKER_IDLE_MINUTES`, the minimum included"; `WORKER_STOP_WHEN_UNUSED=false` only turns off the idle stop for an enabled Worker).
- Test: `backend/test/workers.test.ts`, "still stops its containers after the idle timeout".
- Fix: for a disabled Worker the idle timeout applies even when `stopWhenUnused` is false; busy containers still finish their Jobs.

### Job lifecycle around a Worker Container

#### A Job with a live Runner but a stuck `claude` has no timeout (to confirm)

- Where: `backend/src/runner/handlers.ts:237`, `backend/src/sessions/lifecycle.ts:353`, `runner/internal/runner/job.go:228`
- Behaviour: after `job.result` the backend sets the Job `finishing` and waits for `job.exited`; if `claude` hangs (or its process never exits), the Job stays active. Stop answers `409` in `finishing`, and recovery only runs when the Runner disconnects.
- Why it might be a bug: the Worker Container stays busy and its Queue waits, which matches the reported "wedged Worker" symptom, yet the platform does nothing until someone restarts the container.
- Why it might be intended: Turns and tools can legitimately run long, and the specs set no Turn or Job timeout.

### Runner process and container entrypoint

#### A Runner that cannot open its credential socket stays alive and unconnected forever (to confirm)

- Where: `runner/internal/runner/runner.go:50`, `runner/internal/runner/credentials.go:73`
- Behaviour: if `serveCredentials` fails (path is not a socket, permissions, a full/read-only temp directory), `Run` returns. `main` keeps waiting for a signal, so the process stays alive, never retries and never reconnects; Docker's restart policy never fires because the process did not exit.
- Why it might be a bug: a transient or environmental failure permanently wedges the Worker Container until it is recreated by hand; this is another way the reported symptom appears.
- Why it might be intended: `docs/specs/runner.md` explicitly says "When the socket fails to open, the Runner logs the error and stays idle, unconnected". Changing it needs a spec decision (retry, or exit so Docker restarts).

### Image Builds and Platform Version upgrades

#### Jobs on old containers are told about newly selected services during or after a failed Build (to confirm)

- Where: `backend/src/sessions/dispatch.ts:306`, `backend/src/agents/scheduler.ts:230`
- Behaviour: `PATCH /workers/:id` stores the new `services` immediately, but existing containers keep the old image and its services until a successful Build recreates them. `dispatchEntry` builds the system prompt from `worker.services`, so during the Build (and permanently after a failed Build) the Agent is told about services that are not running, and not about ones that are.
- Why it might be a bug: `docs/specs/workers.md` says a failed Build keeps the previous containers and their services in service, and the Agent learns the selected services from its system prompt.
- Why it might be intended: the configuration is the desired state and the old containers are temporary; no spec says the prompt must describe the image currently running in the chosen slot.

### Worker API actions and Queue management

#### A manually restarted idle container was stopped again immediately

- Where: `backend/src/modules/workers/routes.ts:140`
- Problem: Restart called Docker and then the reconciler, but did not refresh `idleSince`. An idle container above the minimum was already past `WORKER_IDLE_MINUTES`, so the same request's reconcile stopped it again; the button looked like a no-op.
- Spec: `docs/specs/workers.md` ("Restart ... restarts the existing running container").
- Test: `backend/test/workers.test.ts`, "gives a manually restarted idle container a fresh idle window".
- Fix: a successful Restart refreshes `idleSince` and marks the Runner disconnected until its `hello`; the container gets a full idle window.

### Workers UI

#### At 700 px the Queue rows no longer showed their Task

- Where: `frontend/src/pages/WorkerPage.tsx:369`
- Problem: the Task link was `min-w-0 flex-1 truncate`; with a long Agent name the flexible link collapsed to zero width. All Queue rows showed only the Agent, state and action buttons, so a User could not tell which Task an Entry belonged to.
- Spec: `docs/specs/workers.md` ("the Worker's Queue, each entry with its Task and Agent").
- Test: `frontend/e2e/workers.spec.ts`, "keeps the Task visible in a Queue row on a narrow screen".
- Fix: the row wraps, the Task link keeps a minimum width, and the Agent name is capped and truncated.
- Screenshots: [before](bug-hunt-2026-11-03/queue-before.png) · [after](bug-hunt-2026-11-03/queue-after.png)

#### Archived Projects on a Worker linked to `/p/<uuid>`

- Where: `frontend/src/pages/WorkerPage.tsx:452`, `backend/src/modules/workers/service.ts:68`
- Problem: the Projects tab resolved each Project's Key from `GET /projects?archived=false`. An archived Project is still listed by the Worker but absent from that list, so its link used the UUID and answered "Project not found"; a failed Projects request degraded every link the same way without an error.
- Spec: `docs/specs/workers.md` ("Projects: the Projects of every kind that run on the Worker").
- Test: `frontend/e2e/workers.spec.ts`, "links an archived Project on a Worker by its key".
- Fix: `loadWorkers` carries each Project's Key in the Worker payload; the Projects tab no longer depends on a second list.

#### Stopped slots above the cap stay in the Containers tab (to confirm)

- Where: `backend/src/modules/workers/service.ts:82`
- Behaviour: the tab renders slots from 1 to `max(cap, highest existing slot)`, so slots above a lowered cap remain listed after they are stopped. `docs/specs/workers.md` says the tab shows "one row per slot, from 1 to the cap plus any slot above the cap that is still running"; the existing Worker test expects `[1, 2, 3]` after lowering the cap to 1.
- Why it might be a bug: it contradicts that sentence and keeps rows for containers that no longer run.
- Why it might be intended: those slots keep their containers and Service Volumes for a later cap increase, and showing them tells an Admin their databases survive.

### Worker persistence, migrations and concurrency invariants

#### A pending recreation can interrupt a Job dispatched after the reconciler's snapshot (to confirm)

- Where: `backend/src/agents/scheduler.ts:343`, `backend/src/agents/scheduler.ts:464`
- Behaviour: `reconcileOnce` reads the active Jobs once, then calls `recreate` without the Worker row lock. A Job dispatched between that read and the Docker call is not seen as busy; with a pending image/limits recreation, the container is recreated under it. The Job is recovered afterwards and resumes, but the spec says recreation waits until the container has no active Job.
- Why it might be a bug: `docs/specs/workers.md` ("it waits until that container has no active Job") and an Admin's image/limits change can interrupt work unexpectedly.
- Why it might be intended: the window is short, the Job resumes, and the alternative is a reconciliation lock held across Docker calls. Fixing it needs a transaction that rechecks the Job and marks the container as recreating before Docker runs.
