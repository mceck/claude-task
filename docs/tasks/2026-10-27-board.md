# Board: Projects, Statuses, Tags and Tasks

## Specs

- [Board](../specs/board.md)

## Problem Statement

The team wants to delegate development work to Claude Code Agents. Before Agents can do anything, the work needs a place to live: Projects with their own workflow, a kanban Board per Project, Tasks with readable identifiers and rich descriptions, and a complete history of who changed what. Off-the-shelf boards can't host the platform's own Agents, so the team needs its own board that Users and Agents edit side by side, live, without overwriting each other.

## Solution

A self-hosted board. Users create Projects with a short, fixed Project Key; each Project starts with six default Statuses grouped into Categories (`open`, `active`, `review`, `done`, `closed`) that the team can rename, recolor, reorder, recategorize and delete. Tasks get sequential Task Keys like `API-42`, a Markdown description, a priority, Tags, User assignees and at most one Agent, and live in a drag-and-drop Board with one column per Status and closed columns hidden by default. Every field change is recorded as a Revision; edits use per-field optimistic concurrency, while moves never conflict. Board changes appear live for everyone. Projects can be archived and, by Admins, deleted for good.

## User Stories

1. As a Member, I want to create a Project with a name and a short uppercase key (e.g. `API`), so that Tasks get readable identifiers like `API-42`.
2. As a Member, I want a key suggested from the Project name, so that creating a Project is quick.
3. As a Member, I want Project Keys to be unique and fixed, so that Task Keys never change or collide.
4. As a Member, I want a new Project to start with a sensible default set of Statuses, so that I can begin working immediately.
5. As a Member, I want to edit a Project's name and description, so that it stays accurate.
6. As a Member, I want to open a Project by its key in the URL, so that links are readable.
7. As a Member, I want to see all Projects with Task counts per Category and a progress bar, so that I can see where work stands.
8. As a Member, I want to archive a Project, so that it disappears from the main list without losing its history.
9. As a Member, I want to unarchive a Project and browse archived ones, so that I can resume work on them.
10. As an Admin, I want to permanently delete an archived Project with its Tasks, Comments and attachments, so that I can remove test Projects and reuse their key.
11. As an Admin, I want deleting a Project refused while an Agent is working in it, so that no running Job loses its Task.
12. As a Member, I want to add, rename, recolor and reorder a Project's Statuses, so that the Board fits that Project's workflow.
13. As a Member, I want each Status to belong to a Category, so that the system and Agents understand what a Status means regardless of its name.
14. As a Member, I want to be prevented from removing the last `open` or the last `closed` Status, by deletion or recategorization, so that the Project always has an entry point and an exit.
15. As a Member, I want to delete a Status only after choosing where its Tasks go, so that no Task is left without a Status.
16. As a Member, I want Tasks moved by a Status deletion recorded on each Task, so that their history explains the move.
17. As a Member, I want Status names unique within a Project regardless of case, so that columns are never ambiguous.
18. As a Member, I want `closed`-category Statuses hidden from the Board by default with a toggle to show them, so that the Board stays focused on live work.
19. As a Member, I want to create Project-scoped Tags with colors and attach several to a Task, so that I can categorize work.
20. As a Member, I want to create a Tag directly from a Task's Tag picker, so that I don't have to leave the Task.
21. As a Member, I want deleting a Tag to take it off every Task with a Revision, so that history shows why it disappeared.
22. As a Member, I want to create a Task with a title in a given column directly from the Board, so that capturing work is fast.
23. As a Member, I want each Task to get a sequential per-Project number, unique even under concurrent creation and never reused, so that I can reference it in conversation and branch names.
24. As a Member, I want to write the Task description in Markdown with checklists and code blocks, edited in place, so that I can give structured instructions.
25. As a Member, I want to set a Task's priority (urgent, high, normal, low, none), so that important work stands out.
26. As a Member, I want to assign one or more people to a Task, so that it's clear who is responsible or reviewing.
27. As a Member, I want to drag a Task between columns to change its Status, so that updating the Board is one gesture.
28. As a Member, I want to drag a Task within a column to reorder it, so that I can express ordering inside a Status.
29. As a Member, I want a failed drag to put back only that card and tell me why, so that I never trust a move that didn't happen.
30. As a Member, I want Board changes made by others, including Agents, to appear live without reloading, so that I never act on stale information.
31. As a Member, I want to filter the Board by assignee (including unassigned), Tag, priority and free text on title or key, combined, so that I can focus on a subset of Tasks.
32. As a Member, I want to open a Task in a large dialog without leaving the Board, so that I keep my context.
33. As a Member, I want a direct URL for each Task and a "Copy link" action, so that I can share it.
34. As a Member, I want to see who created a Task and when, and when it was last updated, so that I have context.
35. As a Member, I want every field change (Status, title, description, priority, Tags, assignees, Agent) recorded with its author, before and after, so that I can see what happened and who did it.
36. As a Member, I want my edit refused with the current Task when someone changed the same field meanwhile, so that I never silently overwrite their work.
37. As a Member, I want edits to different fields of the same Task to go through together, so that two people working on one Task don't block each other.
38. As a Member, I want quick successive edits of mine never to conflict with each other, so that fast editing just works.
39. As a Member, I want to delete a Task with confirmation, so that I can remove mistakes.
40. As a Member, I want deleting a Task refused while an Agent is working on it, so that a running Job never loses its Task.
41. As a Member, I want Task cards to show key, title, priority, Tags, assignee avatars, Agent state, pull request and Comment count, so that I can scan the Board.
42. As a Member, I want Task Keys to work in any letter case in URLs, so that typed links still open.
43. As an Agent, I want my changes to my Task recorded as Revisions attributed to me, so that my actions are auditable.

## Implementation Decisions

- **Modules**: Projects (create, edit, archive, unarchive, permanent deletion, list with per-Category counts, lookup by id or key), Statuses (per-Project ordered list with Categories, the open-and-closed invariant, delete with relocation), Tags, and Tasks (numbering, ordering, filters, the concurrency check, Revisions, card projection, Session lifecycle hook on Status and Agent changes). An Actor resolver loads display names in one batch.
- **Projects**: key 2 to 6 uppercase letters, unique, fixed; name 1 to 100 characters, description up to 10,000. A kind column distinguishes ordinary Projects from Wiki Projects, which the list leaves out. Archiving keeps the first archive time. Permanent deletion is Admin-only, requires an archived Project and no active Job on its Tasks, removes Worktrees, Tasks and stored files after commit, and frees the key.
- **Default Statuses**: Backlog (open), Todo (open), In Progress (active), Ready for Review (review), Done (done), Closed (closed), with fixed colors.
- **Statuses**: name 1 to 100 characters, unique per Project case-insensitively; `#rrggbb` color; reorder takes the full permutation; delete takes a target Status of the same Project and moves the Tasks to its end in order, each with a version bump and a Revision. Recategorizing into or out of `closed` closes or reopens the Sessions of its Tasks. Every Status change locks the Project row.
- **Tags**: same name and color rules; deleting detaches the Tag from its Tasks with a Revision and version bump on each.
- **Tasks**: title 1 to 500 characters, description up to 100,000, priority default `none`, up to 50 Tags (same Project) and 50 assignees (existing Users), Status default the first `open` one. The number comes from a counter on the Project row, incremented in the creating transaction. Version starts at 1.
- **Concurrency**: updates carry the version the client saw; a newer-than-current version, or a touched field changed in a Revision since that version, gets `409` with the current Task. No-op updates write nothing. Moves (Status plus neighbours) never conflict; same-Status moves leave version and history untouched. Deadlocks and serialization failures answer `409` `retry`.
- **Ordering**: fractional index keys compared byte by byte; a Status change through an update goes to the end of the column; duplicate keys from concurrent moves are repaired by renumbering the column.
- **Revisions**: written in the same transaction as each change, unique per (Task, version), with Actor and per-field before and after; Tag and assignee lists stored sorted.
- **Filters**: assignee ids or `none`, Tag ids, priorities, text up to 200 characters on title or Task Key; OR within a kind, AND across kinds; closed Tasks only on request. The matching rule is shared with the clients.
- **Realtime**: events released after commit. Project topic: `task.created`, `task.updated`, `task.moved`, `task.deleted`, `statuses.changed`, `tags.changed`, `project.updated`. Task topic: `task.changed`, `task.removed`, `revision.created`.
- **Web views**: Projects list with archived switch and New project dialog; Board with filter bar, "Show closed" switch in the URL, columns with counts and "Add task", drag and drop with optimistic updates and per-card rollback; Task dialog over the Board (Task Key in the URL) and full Task page; Task details with Status, priority, assignees, Agent, Tags (with inline creation), created and updated info, title edited inline, description edited in place and saved once per editing session; Project settings with General, Statuses, Tags, Agents and Repository tabs.

## Testing Decisions

- Seam 1, the backend public API against real Postgres: Project creation with default Statuses, key validation, uniqueness and immutability, lookup by key, archiving lists, per-Category counts, permanent deletion rules and cleanup; Status add, rename, recolor, uniqueness, validation, reorder permutation, the open-and-closed invariant on delete and recategorize, delete with relocation and Revisions, edits racing deletions; Task numbering (sequential, concurrent, not consumed on failure, never reused), defaults, creator, column placement, cross-Project validation, lookup by key in any case, card fields, closed Tasks hidden by default, every filter and their combination, updates with Revisions, no-op updates, stale-version conflicts and per-field merging, moves to top, end and between neighbours, many moves into one gap, concurrent moves, moves racing a Status deletion, deletion; Tags with detach Revisions; realtime board and task topic events, after commit only. Prior art: the projects, tasks and realtime test files with the shared fixtures and WebSocket test client.
- Members' `403` on permanent deletion is covered with the user management tests.
- Seam 3, Playwright against the real backend: creating a Task from the Board, dragging between and within columns seen live in another browser, hiding closed Statuses until toggled and combining filters, Task dialog and page, in-place description editing saved once, a failed move putting back only that card, quick consecutive Tag toggles all saved, and a late save response not undoing a newer live change.

## Acceptance Criteria

- [x] Creating a Project creates the six default Statuses; Project Keys are 2 to 6 uppercase letters, unique and immutable.
- [x] Projects are reachable by id or key; the Projects list shows non-archived ordinary Projects with Task counts per Category, and archived ones on request.
- [x] Only Admins can permanently delete a Project, only once archived and with no active Job; its Tasks, Comments and attachments go with it and its key becomes free.
- [x] A Project always has at least one `open` and one `closed` Status; deleting a Status requires a target Status and moves its Tasks there with a Revision each.
- [x] Status and Tag names are unique within a Project regardless of case; colors are `#rrggbb`.
- [x] Deleting a Tag removes it from every Task with a Revision on each.
- [x] Task numbers are sequential per Project with no duplicates or gaps, even when Tasks are created concurrently, and are never reused.
- [x] Tasks are reachable by id or Task Key in any letter case.
- [x] Dragging a Task to another column changes its Status, dragging within a column reorders it, and both persist across reloads and appear live in another browser.
- [x] Task updates create Revisions with Actor, before and after; no-op updates create none.
- [x] A stale update touching a field changed since its version returns `409` with the current Task and writes nothing; one touching only unchanged fields is applied.
- [x] Moves never conflict, and concurrent moves into the same gap lose no Task.
- [x] Deleting a Task with an active Agent Job is refused with `409`.
- [x] `closed`-category Statuses are hidden on the Board by default and shown with the toggle.
- [x] Board filters (assignee including unassigned, Tag, priority, text on title or key) work together.
- [x] Board and Task events reach subscribed clients only after commit.

## Out of Scope

- Agents, Sessions, the Agent Timeline and Task Tools (Agents and Agent Sessions work).
- Comments, Internal Notes, attachments and notifications (Conversation work).
- Repository link, Task Branches and pull requests (Git integration work).
- Subtasks, due dates, time tracking, custom fields, other views (list, calendar, gantt), saved filters.
- Per-Project permissions, multiple workspaces.
- Full-text search beyond the Board's text filter.

## Further Notes

- Depends on [Users and authentication](2026-10-27-users-and-auth.md) for Logins and roles.
- The Task version and Revisions exist from the start because the Agent runtime's Notify agent feature and Unseen Changes build on them.
- Wiki Projects (kind `wiki`) were added later by the Wikis work and are only filtered out of the Projects list here.
