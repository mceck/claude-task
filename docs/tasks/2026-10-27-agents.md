# Agents: configuration, Credentials, Base Image and runtime

## Specs

- [Agents](../specs/agents.md)

## Problem Statement

We want Claude Code agents to work on our Tasks like teammates, but running one by hand means opening a terminal per Task, installing toolchains on a laptop, pasting API keys into shells and babysitting processes that die with the terminal. There is no shared definition of "the agent that does backend work": each person sets up their own, with their own tools, versions and credentials, and nobody else can see what it is doing or whether it is stuck.

Admins need to define a few reusable Agents once (who they are, which Claude account and model they use, which toolchains and local services they need, which shared skills, MCP servers and plugins they get) and have the platform keep each one running in its own isolated, reproducible environment. Secrets must stay safe: they must not leak through the UI, the API, logs or the container's own environment, and a rotated key must take effect without rebuilding anything.

## Solution

Admins define **Agents** in the app: a name and avatar, a **Credential** (a Claude OAuth token or an Anthropic API key, stored encrypted and write-only), model, effort, permission mode, system prompt, a Dockerfile that starts from the platform's **Base Image**, a selection of local development services, resource limits, and Extensions from a shared catalog. Every User sees the Agents, their state and what they are working on.

The backend builds each Agent's image locally through the host's Docker socket, on top of a Base Image that carries a centrally pinned `claude` CLI, the Runner and the non-root `agent` user, and runs it as one long-lived **Agent Container** with a persistent **Agent Volume**. A reconciler keeps every container in line with its configuration: it rebuilds images when the Dockerfile, services or platform change, recreates containers only when the Agent is idle (unless forced), restarts stopped containers and synchronizes Skills and Plugins between Jobs. A failed build leaves the working container in place.

Credentials and Project environment variables travel with each Job instead of living in the container, so rotation applies on the next Job and Project secrets reach only that Project's Tasks. The Runner token that connects the container to the backend reaches only the Runner process.

## User Stories

### Credentials

1. As an Admin, I want to store a Claude credential (an OAuth token from `claude setup-token` or an Anthropic API key) under a name, so that Agents can authenticate with it.
2. As an Admin, I want a Credential's secret to be write-only, with only its last four characters shown after saving, so that it can't be read back through the app.
3. As an Admin, I want short secrets to show no hint at all, so that four characters don't reveal most of a short value.
4. As an Admin, I want to rotate a Credential's secret in place, so that every Agent using it picks up the new value on its next Job without reconfiguration or rebuild.
5. As an Admin, I want to rename a Credential while its kind stays fixed, so that its meaning stays stable for the Agents that use it.
6. As an Admin, I want to see which Agents use a Credential, so that I understand the impact of rotating or deleting it.
7. As an Admin, I want deleting a Credential that is in use to be refused with the names of its Agents, so that no Agent is left unable to run.
8. As an Admin, I want to see the latest rate-limit status observed for each Credential, so that I know when an account is close to its limits.
9. As a Member, I want the Credentials page to be hidden from me, so that only Admins handle Claude secrets.

### Creating and configuring Agents

10. As an Admin, I want to create an Agent with a name, an emoji and a color, so that people recognize it on the board.
11. As an Admin, I want to upload an avatar image for an Agent (PNG, JPEG, GIF or WebP up to 2 MB), so that it has a recognizable face.
12. As an Admin, I want to remove an Agent's avatar image, so that its emoji and color show again.
13. As an Admin, I want Agent names to be unique ignoring case, so that people never confuse two Agents.
14. As an Admin, I want to write a description for an Agent, so that people know what it is for.
15. As an Admin, I want to pick the Agent's Credential (required), so that I control which account and rate limits it consumes.
16. As an Admin, I want to set the Agent's model and effort level, or leave them to Claude's defaults, so that I can trade cost for capability per Agent.
17. As an Admin, I want to set the Agent's permission mode (`bypassPermissions` by default; also `auto`, `acceptEdits`, `dontAsk`), so that I decide how much freedom it has inside its container.
18. As an Admin, I want to give the Agent its own system prompt, so that it follows consistent working rules, e.g. "always write tests".
19. As an Admin, I want to write the Agent's Dockerfile in the app with syntax highlighting, so that it has the toolchains our Projects need.
20. As an Admin, I want a Dockerfile that doesn't start from the Base Image to be rejected on save with a clear message, so that every Agent keeps the Runner, the pinned CLI and the agent user.
21. As an Admin, I want `ARG` instructions, a tag, a digest, a `--platform` flag or a stage name on the first `FROM` to be accepted, so that ordinary Dockerfile conventions keep working.
22. As an Admin, I want a build whose image doesn't end as `USER agent` to fail with an explanation, so that `bypassPermissions` never meets a root user.
23. As an Admin, I want to set CPU and memory limits for an Agent's container, so that one Agent can't starve the host.
24. As an Admin, I want to disable an Agent, so that it stops taking new work without being deleted and without losing its Queue.
25. As an Admin, I want to duplicate an Agent with all its settings, avatar and Extensions, under a free "(copy)" name, so that I add throughput with the same environment.
26. As an Admin, I want to delete an Agent that has no open Sessions, together with its container, images and volume, so that I can clean up.
27. As an Admin, I want deleting an Agent with open Sessions to be refused with the Task keys that still hold one, so that I know what to unassign first.
28. As a Member, I want closed Tasks still assigned to a deleted Agent to be unassigned with a visible Revision, so that the board stays truthful.
29. As an Admin, I want changes to model, effort, permission mode, system prompt or Credential to apply from the next Job without a rebuild, so that tuning an Agent is cheap.
30. As an Admin, I want changing CPU or memory limits to recreate the container without rebuilding the image, so that limits apply quickly.

### Agent state and visibility

31. As a Member, I want to see every Agent with its state (building, build failed, offline, idle, working, disabled), current Task, Queue length, Credential and last activity, so that I know who's free and who's stuck.
32. As a Member, I want to open an Agent and see its container state and whether its Runner is connected, so that I can tell an environment problem from a slow Job.
33. As a Member, I want to see an Agent's build history with each build's log, so that I can understand why it's not ready.
34. As a Member, I want to see an Agent's usage (cost, tokens and Turns, per day for 30 days and per Task) and its Credential's latest rate-limit status, so that I understand consumption.
35. As a Member, I want Agent changes, build progress and build logs to update live, so that I don't refresh the page.
36. As a Member, I want to see that a container recreation is waiting for the current Job to end, so that I know when a change will apply.
37. As a Member, I want an Agent with a failing build to keep working on its previous image, so that a typo doesn't stop the team.

### Images and containers

38. As an Admin, I want an Agent's image to build automatically when I create it or change its Dockerfile or services, so that its environment always matches its configuration.
39. As an Admin, I want to watch build output live, so that I can fix a broken Dockerfile quickly.
40. As an Admin, I want a failed build to keep the previous image and container running and mark the Agent as build failed, so that a mistake doesn't take a working Agent offline.
41. As an Admin, I want a rebuild requested during a build to run once after it, so that the latest configuration always gets built.
42. As an Admin, I want a build interrupted by a backend restart to be marked failed and rebuilt automatically, so that no Agent stays stuck in "building".
43. As an Admin, I want to rebuild an Agent's image by hand, so that I can pick up upstream package updates.
44. As an Admin, I want to restart an Agent's container, so that I can recover from odd states.
45. As an Admin, I want a container recreation to wait until the Agent's current Job ends, with an option to force it, so that I don't kill work in progress by accident.
46. As an Admin, I want a forced recreation or a restart to resume the interrupted Turn afterwards, so that work isn't silently lost.
47. As an Admin, I want an Agent's repositories, Worktrees, Claude Sessions, service data and tool installs to survive container recreation, so that rebuilding never loses work.
48. As an Admin, I want a stopped or crashed container to be restarted automatically, so that Agents heal without me.
49. As an Admin, I want to read an Agent container's recent logs, so that I can debug the Runner and the services.
50. As an Admin, I want old images of an Agent pruned once a new container runs, so that the Docker host doesn't fill up.

### Base Image and platform version

51. As the operator, I want the Claude Code version used by all Agents to be pinned centrally, with the auto-updater off, so that every Agent runs a tested version of the stream format and upgrades are deliberate.
52. As the operator, I want the Base Image built locally by the backend from bundled sources, so that I need no registry and no source checkout in production.
53. As the operator, I want changing the pinned version, the Base Image recipe or the Runner to rebuild every Agent's image and recreate each container when its Agent is idle, so that upgrades roll out by themselves without killing work.
54. As an Admin, I want my Dockerfile built against the exact current Base Image whatever tag it names, so that every Agent runs the current platform.

### Development environment

55. As an Admin, I want to choose which local development services (PostgreSQL, Redis, MySQL, Mailpit, RustFS) run in an Agent's container, with PostgreSQL and Redis by default, so that Agents can run tests against real services.
56. As an Admin, I want to select no services at all, so that a lean Agent stays lean.
57. As an Agent, I want the services to listen on loopback with well-known addresses and no passwords, so that I can use them without configuration.
58. As an Admin, I want service data to persist in the Agent Volume and survive deselecting and reselecting a service, so that databases aren't lost by a configuration change.
59. As an Admin, I want changing the service selection to rebuild the image and follow the wait-for-idle rule, so that the change is safe.
60. As an Agent, I want the tool versions my repository declares for mise installed before the Setup Script, so that the right runtimes are ready.

### Project environment

61. As an Admin, I want to define a Project's environment variables, plain or secret, so that Agents working on that Project's Tasks (and only those) get them.
62. As an Admin, I want secret variables to be write-only with only their last four characters shown, so that they can't be read back.
63. As an Admin, I want names the platform sets itself (Credential variables, the resume flag, `CLAUDE_TASK_*`, `HOME`, `PATH`, `USER`) to be rejected, so that a Project can't break its Agents.
64. As an Admin, I want to import a `.env` file merged into the existing variables, with a preview of new and overwritten names, so that I can set up a Project quickly.
65. As an Admin, I want an import to keep existing secrets secret and optionally import everything as secret, so that an import never downgrades a secret.
66. As an Admin, I want an invalid `.env` file to write nothing and tell me which lines are wrong, so that a half-applied import never happens.
67. As a Member, I want to see a Project's variable names and plain values, so that I know what the Agents get.
68. As a Member, I want to write a Project's Setup Script and Agent Instructions, so that every Agent is ready and follows our conventions.

### Extensions

69. As an Admin, I want to import Skills from a GitHub `owner/repo`, an HTTPS URL or a Git SSH URL into a shared catalog, so that Agents share curated skills.
70. As an Admin, I want an import to keep a snapshot of every file, scripts and binary assets included, with their executable bit, so that Skills work exactly as published.
71. As an Admin, I want imports limited in size and checked for a valid `SKILL.md`, safe names and no symbolic links, so that the catalog stays safe.
72. As an Admin, I want to reimport a Skill to fetch its newer content while keeping its assignments, so that updates are one click.
73. As an Admin, I want to register MCP servers (HTTP, SSE or stdio) with secret headers or environment values, so that Agents reach our tools without exposing tokens.
74. As an Admin, I want saved MCP secrets to stay hidden and be kept when I edit an entry without retyping them, so that editing is safe.
75. As an Admin, I want to add Plugins from a marketplace to the catalog, so that Agents use them the normal Claude Code way.
76. As an Admin, I want to update a Plugin to the marketplace's latest version for every Agent using it, so that upgrades are one click.
77. As an Admin, I want to assign Skills, MCP servers and Plugins per Agent, so that each Agent gets only what it needs.
78. As an Admin, I want catalog changes to apply to an Agent before its next Job without rebuilding its image or recreating its container, so that they are cheap.
79. As an Admin, I want a failing Skill or Plugin synchronization shown on the Agent and holding its next Job until it succeeds, so that an Agent never works with a half-configured environment.
80. As an Admin, I want Skills and Plugins installed by hand in an Agent's home left untouched, so that manual setup survives synchronization.
81. As an Admin, I want a catalog entry that's still assigned to be protected from deletion, so that no Agent loses it unexpectedly.
82. As a Member, I want Comments to keep flowing while a slow Plugin installation runs, so that the app never stalls on Docker.

### Security of the runtime

83. As the operator, I want Claude credentials and Project secrets sent per Job instead of baked into container environment, so that rotation is immediate and secrets stay scoped.
84. As the operator, I want all secrets encrypted at rest with a master key the backend requires to start, so that a database dump reveals nothing.
85. As the operator, I want the Runner token to reach only the Runner process, so that code the Agent runs can't impersonate its Runner.
86. As the operator, I want the Runner token rotated on every container recreation and refused when unknown or outdated, so that an old token stops working with its container.
87. As the operator, I want a Runner that stops answering pings dropped, so that its Job can be recovered instead of looking connected forever.

### Deployment

88. As the operator, I want to run the whole platform with Docker Compose, with Agent Containers reaching the backend on a dedicated network, so that I need no extra infrastructure.
89. As a developer, I want a fake runtime that simulates images and containers, so that tests and demos run without Docker.

## Implementation Decisions

- **AgentRuntime** is the only module that talks to Docker. Its interface: the Base Image version; ensure the Base Image; build an Agent Image (with a log callback, returning the image tag and its final user); create a container (replacing any existing one, keeping the volume); restart; inspect; read logs; remove an Agent (container, images, volume); synchronize Skills; synchronize Plugins. Two implementations: Docker over the mounted socket, and an in-memory fake used by tests and the `fake` runtime setting.
- **Platform Version** = pinned Claude Code version plus the first 12 hex characters of a SHA-256 over the version, the Base Image recipe, its service and entrypoint scripts, and the Runner's Go sources (tests excluded). The Base Image is built lazily, as the first step of any Agent Build, when the image for that version is missing, and is also tagged `latest`.
- **Base Image**: Ubuntu 24.04 (`buildpack-deps:noble`), Claude Code installed under a path outside the agent's home, Runner and git credential helper compiled in a Go build stage, git's system credential helper set to the platform helper, uid 1000 user renamed or created as `agent`, mise copied from its official image, `DISABLE_AUTOUPDATER=1`, the path to `claude` set for the Runner, mise shims on `PATH`, final user `agent`.
- **Dockerfile rules**: shared validation used by the backend on save and the form while editing. At build time the first `FROM` is rewritten to the exact Platform Version, and a root step installing the selected services plus an environment variable naming them are inserted right after it. The built image's final user must be one of `agent`, `agent:agent`, `1000`, `1000:1000`.
- **Scheduler** owns background work: one Build per Agent at a time with one follow-up queued; a per-Agent serialized reconciler; a 30-second tick that reconciles every Agent, recovers Jobs whose Runner stayed away more than 5 minutes and dispatches Agents with waiting Queue Entries; coalesced real-time publishing.
- **Builds**: a Build row per attempt with the Dockerfile as saved, Platform Version, status, image tag and log (tail of 256 KB, flushed every 500 ms, streamed as chunks on the Agent's topic). Agent image state is `none`, `building`, `built` or `failed`; a failed Build leaves the previous image tag in place. On startup, Builds still marked `building` become failed with a note and their Agents go back to `none`.
- **Container recreation**: the Agent row stores the JSON of the image and limits the container was created with; the reconciler compares it to the desired one. Recreation waits for no active Job unless the container is missing or a force flag is set by the Admin's Force recreate. Recreating generates a new Runner token (only its hash is stored), closes the old Runner connection with a dedicated close code, and resets the applied Extensions revision so the new container is synchronized again. After a new container starts, older images of the Agent are removed.
- **Container shape**: name and volume named after the Agent id, label with the Agent id, restart policy `unless-stopped`, volume mounted at the agent home, network from the `AGENT_NETWORK` setting or the default bridge, `host.docker.internal` mapped to the host gateway, CPU and memory limits, environment limited to the Runner WebSocket URL and the Runner token.
- **Agent state** is derived on read: disabled, then building, then build failed, then offline (Runner not connected), then working (an active Job) or idle. Dispatch readiness checks enabled, Extensions revision applied, Runner connected, container running and created with the desired spec, and no active Job. It does not look at the image state, so an Agent whose latest Build failed keeps working on its previous container.
- **Runner token handling**: the entrypoint re-executes itself without the token and reads it back from an inherited pipe; it starts services without the token and passes it only to the Runner. The Runner unsets the token and the backend URL from its own environment, marks itself non-dumpable, and starts child processes with an environment that excludes the token. Backend execs into the container run as `agent` with the token variable blanked, a fixed home, no terminal prompts for git and a 5-minute timeout.
- **Runner connection**: WebSocket authenticated by bearer token, mapped to one Agent through its hash; `401` for unknown tokens; a newer connection replaces an older one; ping every 30 seconds and termination after a missed round. Close codes distinguish replacement, recreation and deletion.
- **Credentials API** (Admin only): list, get, create, update (name and secret), delete. Responses carry name, kind, last four characters (empty under 12 characters), Agents using it and the latest rate-limit observation. Delete is refused with `409` while referenced; the database also restricts it. Credential env var per kind: `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`.
- **Secret box**: AES-256-GCM with a random 12-byte IV and a `v1` key-version prefix, keyed by `SECRETS_MASTER_KEY` (32 bytes, base64 or hex). Used for Credentials, secret Project variables, secret MCP values, Git Connection credentials and push tokens. Loading configuration fails without a valid key.
- **Agents API**: reads, Builds, Queue, Jobs and usage open to every User; create, update, delete, duplicate, rebuild, restart, recreate (with `force`), logs (tail 1 to 5,000, default 500) and avatar upload or removal for Admins. Field limits: name 1–100 (unique ignoring case), emoji 1–16, color hex, description ≤ 2,000, Dockerfile 1–100,000, model 1–100 or null, effort enum or null, permission mode enum, system prompt ≤ 50,000, CPU > 0 and ≤ 256 or null, memory 256–1,048,576 MB or null, services from the five known values without duplicates, up to 100 Skills, MCP servers and Plugins each. A PATCH rebuilds only when the Dockerfile text or the service selection actually changes; otherwise it reconciles (which covers limit changes) and dispatches.
- **Deletion**: one transaction unassigns the Agent from its Tasks with Revisions by the Admin, then refuses with `409` (listing Task keys) if any Session is `pending`, `idle` or `running`. On success the Agent's dependent rows cascade, the Runner is disconnected, and Docker cleanup runs in the background with failures logged.
- **Duplicate**: copies every setting, the avatar (as a new blob, deleted again if the copy fails) and the Extensions assignments; name from the request or the first free "(copy)", "(copy N)" within 100 characters.
- **Project agent settings**: Setup Script and Agent Instructions editable by every User; environment variables managed by Admins (put, `.env` import, delete), with reserved names rejected, values up to 100,000 characters, imports up to 500,000 characters and 500 variables, applied atomically, secrets never downgraded by an import. A shared dotenv parser runs both for the import and for the client-side preview.
- **Job environment**: Project variables, then the Credential's variable, then the resume flag, later ones winning; decrypted only while building the Job's start payload.
- **Extensions**: catalog tables for Skills (unique name, source, files, content hash, user-invocable flag), MCP servers (unique name, transport, URL or command and args, headers and env as plain or encrypted values) and Plugins (unique name and source), with assignment tables restricting deletion of assigned entries. Each Agent has an Extensions revision, the revision last applied and the last error. Any assignment change, reimport, MCP edit or Plugin update bumps the revision of the affected Agents and clears their error.
- **Skill import** runs the pinned `skills` CLI from the backend's dependencies in a temporary directory with isolated state and telemetry off, 2-minute timeout, sources limited to `owner/repo`, HTTPS without credentials or Git SSH; total 10 MB and 1,000 files; names 1–64 safe characters; `SKILL.md` frontmatter description required; symbolic links rejected. A name already imported from another source is refused with `409`.
- **Synchronization** runs inside the reconciler when the container is running, the Agent is idle and the revision is behind. The revision and the entries are read under a short lock; Docker work runs with no lock held. Skills are written as a per-revision snapshot in the Agent Volume and linked into the Claude skills directory by a script that only accepts validated names, refuses to replace unmanaged entries and removes stale links and snapshots. Plugins are installed, refreshed and uninstalled with `claude plugin` commands run without a shell, and the list of platform-installed plugins is kept in a state file in the volume.
- **MCP configuration** for each Job merges the assigned catalog servers (secrets decrypted) with the reserved `claude-task` server.
- **Deployment**: the production image bundles the Base Image recipe and Runner sources and includes git and OpenSSH; Docker Compose runs PostgreSQL and the app, mounts the Docker socket, adds the socket's group (`DOCKER_GID`), and joins a `claude-task-agents` network that Agent Containers also join, with `AGENT_BACKEND_URL` pointing at the app service.

## Testing Decisions

- **Seam 1, backend public API** against real PostgreSQL, with the fake AgentRuntime (scripted build outcomes, logs, held builds, container states, platform upgrades, plugin failures) and a fake Runner that authenticates with the container's token. Covered:
  - Agent lifecycle: build, container creation with limits and the two-variable environment, `offline` until the Runner connects then `idle`; live build logs and `building` state; service selection, canonical order, empty selection, no rebuild on unrelated edits; invalid services; Dockerfile validation; wrong final user; failed rebuild keeping the old container; recreation waiting for idle and the old token closed with its code; forced recreation resuming the Job; rebuild on Platform Version change; restarting a stopped container; duplication (settings, names within 100 characters, avatar copies, name conflict); deletion blocked by open Sessions and unassigning closed Tasks with a Revision; Members reading but not changing Agents; unknown Runner tokens; dropping Runners that stop answering pings.
  - Credentials: secret never returned, encrypted at rest, rotation in place, deletion refused in use, Admin only, master key required to load configuration.
  - Project settings: secret variables write-only and Admin-managed, short secrets without hint, reserved names, `.env` import merge rules and atomic failures, Members editing Setup Script and Agent Instructions.
  - Extensions: Skill import, assignment and synchronization without recreation; changes deferred while busy and the next Job carrying new Skills and MCP secrets; encrypted MCP secrets preserved on edit and Admin-only changes; reimport propagating to assigned Agents; validation and duplicates; Plugin install, update and duplication; dispatch held while Plugins fail; Comments flowing during a slow Plugin install.
  - Dispatch with configuration, Credential and Project env in the Job payload; disabled Agents keeping their Queue; Credential failures and rate-limit status (in the Sessions suite).
  - Prior art: the API, WebSocket and fixture helpers of the board suite.
- **Skill import against the real pinned CLI** on a local source, covering supporting files, the executable bit and path-escape rejection.
- **Runner as a black box**: the Runner token stays out of Job processes and git hooks; mise runs before the Setup Script and a mise failure stops the Job and can be retried.
- **Opt-in real Docker**: with a built Base Image, the entrypoint hands the Runner token only to the Runner, not to PID 1, services or docker execs.
- **Browser end-to-end** against the fake runtime and fake Runner: Credentials created and rotated write-only, an Agent configured with build and container logs readable; MCP servers managed without exposing secrets; a marketplace Plugin added and assigned; Skill assignment grouped by source; Members reordering the Queue without managing Agents; Project setup, instructions, write-only secrets and `.env` import.

## Acceptance Criteria

- [x] Credentials and secret variables are returned only as their last four characters after saving and are encrypted at rest.
- [x] The backend refuses to start without a valid `SECRETS_MASTER_KEY`.
- [x] Rotating a Credential keeps its Agents and applies on their next Job.
- [x] Deleting a Credential in use is refused, naming its Agents.
- [x] Creating an Agent builds its image with a live log, creates its container with the configured limits, volume and only the Runner's connection variables, and the Agent shows `idle` once the Runner connects.
- [x] A Dockerfile not based on `claude-task/agent-base` is rejected on save; an image whose final user isn't `agent` fails its Build.
- [x] A failed Build leaves the previous container running and marks the Agent `build_failed`.
- [x] After a rebuild, the container is recreated only when the Agent is idle, unless forced; a forced recreation resumes the interrupted Turn.
- [x] Every recreation issues a new Runner token and the old one stops working.
- [x] Changing the Platform Version rebuilds every Agent's image.
- [x] A stopped container is restarted by the reconciler.
- [x] Duplicating an Agent copies its environment, avatar and Extensions under a unique name.
- [x] Deleting an Agent is refused while it has open Sessions; otherwise it removes the container, images and volume and unassigns remaining Tasks with a Revision.
- [x] Members see Agents, Builds and Queues; every management action answers them `403`.
- [x] Development services are installed only when selected, start as `agent` on loopback, and keep their data across restarts, recreation and deselection.
- [x] Project environment variables reach only that Project's Jobs; reserved names are rejected; `.env` imports merge atomically and keep secrets secret.
- [x] Skills, MCP servers and Plugins sync into a running container between Jobs without a rebuild; a failed sync is shown on the Agent and holds dispatch.
- [x] The Runner token is readable only by the Runner: not by PID 1, development services, Job processes, git hooks or the backend's execs.
- [x] A Runner that stops answering pings is dropped and shown offline.
- [x] The production image builds, and a production-container smoke check reaches an `idle` Agent with real Base Image and Agent Image builds and a real non-root Runner.
- [ ] A full real-Docker run with the real `claude` CLI completes a Job end to end (assign, reply, mid-run comment, Stop, container kill and resume).

## Out of Scope

- Running Agents on several hosts or on Kubernetes; the runtime interface leaves room for it.
- Parallel Jobs within one Agent; throughput comes from duplicating Agents.
- Validating a Credential before its first Job.
- Interactive permission approval from the UI; the permission mode is fixed per Agent.
- Guardrail hooks in the container.
- Network egress allowlists per Agent.
- A live terminal into the Agent Container.
- Managing Plugin options (`userConfig`) or private Plugin marketplaces.
- Rotating `SECRETS_MASTER_KEY` (only the key-version prefix exists).

## Further Notes

- The Sessions, Queue, dispatch, Timeline and Task Tools that run on top of this area, and the Runner protocol, are separate pieces of work described in the Agent sessions and Runner specs; the Git Proxy and credential helper in the Git integration spec.
- The real-CLI behaviour the runtime depends on (mid-turn delivery, interrupt, resume, MCP over HTTP) was verified against Claude Code 2.1.310 and recorded in the Decisions of [Agent sessions](../specs/agent-sessions.md).
- The base Ubuntu packages, the mise binary (taken from its `latest` image) and the Mailpit and RustFS releases are fetched at build time, so two Base Images with the same Platform Version can differ slightly if built at different times.
