# Cleanup of images, volumes and Worker Volume leftovers

## Specs

- [Board](../specs/board.md) (Deleting permanently, Changing the Worker)
- [Workers](../specs/workers.md) (Cleanup, Image Builds, Autoscaling, Worker Volume, Configuration settings, Data model, Decisions)

## Problem Statement

The Docker host of an Installation slowly fills up. Every Platform Version change (a new Claude Code version, Base Image recipe or Runner) leaves the previous Base Image behind, several GB each, and nothing ever removes it. Builds leave untagged images. A stopped Worker Container created with an older Worker Image keeps that image alive. Slots left above a lowered cap keep their containers and Service Volumes forever. A Worker deletion whose background removal failed leaves its containers, images and volumes on the host. Inside a Worker Volume, the Bare Clones and Worktrees of Projects that moved to another Worker or were deleted, and the Agent Profiles of deleted Agents, stay until the Worker is deleted.

Admins have no way to free this space from the platform. They need `docker` on the host and must work out by themselves which resources are still needed, and with several Installations on one host a blind `docker system prune` or volume removal can destroy another Installation's data.

## Solution

The platform runs a **Cleanup** of what its Workers no longer need:

- it runs automatically when the backend starts and every 24 hours;
- old Base Images also go after each successful Build, and stopped Worker Containers on an outdated image as soon as the reconciler sees them;
- an Admin can run one from the Workers list with "Clean up". A confirmation lists what it removes, and the result shows what was removed and roughly how much space was freed;
- the Workers list always shows the last Cleanup, automatic or manual.

A Cleanup removes:

1. Base Images of every Platform Version other than the current one.
2. Untagged images left by Builds of platform images.
3. Worker Images of the Installation's Workers that are not the current image and that no container uses. A stopped Worker Container created with an older image is removed (the slot is created again at its next start, with its volumes intact), so its image can go too.
4. Slots above the cap that have had no Job for 7 days: container, Service Volume and record. A manual Cleanup removes them regardless of age.
5. Containers, volumes and images that carry this Installation's label but belong to a Worker that no longer exists.
6. Inside each Worker Volume, through one of its Runners: the Bare Clones and Worktree directories of Projects that no longer run on that Worker, and the Agent Profiles of Agents that no longer exist. A Worker with no connected Runner keeps the request pending until a Runner connects.

`WORKER_CLEANUP=false` turns the automatic part off; "Clean up" still works.

## User Stories

1. As an Admin, I want old Base Images removed automatically after a platform upgrade, so that each upgrade does not cost several GB of disk forever.
2. As an Admin, I want untagged images left by Builds removed, so that failed and repeated Builds do not pile up.
3. As an Admin, I want a Worker's old Worker Images removed even when some of its slots are stopped, so that scale-to-zero Workers do not keep every image they ever ran.
4. As an Admin, I want a stopped slot on an old image to come back on the current image at its next start with its repositories, Worktrees, transcripts and database data intact, so that the cleanup never costs work.
5. As an Admin who lowered a Worker's cap, I want the slots above it kept for a week and then removed with their Service Volumes, so that I can raise the cap back without losing their databases, but forgotten slots stop taking space.
6. As an Admin, I want "Clean up" to remove slots above the cap at once, so that I can free their space when I know I will not need them.
7. As an Admin, I want the leftovers of a Worker whose deletion failed removed, so that a transient Docker error does not leave GBs behind for good.
8. As an Admin running two Installations on one Docker host, I want each Installation to remove only data-bearing resources it created, so that one never deletes the other's Worker Volumes, Service Volumes or containers.
9. As an Admin, I want the Bare Clone and Worktrees of a Project that moved to another Worker removed from the old Worker Volume, so that a move does not leave a full copy of the repository behind.
10. As an Admin, I want the Bare Clone of a permanently deleted Project removed, so that deleting a Project frees its repository.
11. As an Admin, I want the Agent Profiles of deleted Agents removed from every Worker Volume, so that their Skills and Plugins stop taking space.
12. As an Admin, I want a Worker Volume cleanup to wait for a running Worker Container, so that the platform never starts containers just to clean.
13. As an Admin, I want a Worker Volume cleanup to never remove the Bare Clone, Worktree or Agent Profile a Job is using, so that the cleanup never interrupts work.
14. As an Admin, I want package and tool caches left alone, so that Jobs stay fast.
15. As an Admin, I want a "Clean up" action on the Workers list, so that I can free space now when the disk is full.
16. As an Admin, I want the confirmation to tell me what will be removed, so that I know nothing in use is at risk.
17. As an Admin, I want to see what the Cleanup removed and roughly how much space it freed, so that I know whether it helped.
18. As an Admin, I want to see the last Cleanup on the Workers list, with its time, trigger, results and errors, so that I know the automatic Cleanup is working.
19. As an Admin, I want results from Worker Volumes cleaned later to appear on that Cleanup as they arrive, so that the report becomes complete without a refresh.
20. As an Admin, I want a second "Clean up" while one is running to join the running one, so that concurrent requests do not race each other.
21. As an Admin, I want a Cleanup to skip images that a Build in progress needs, so that cleaning never breaks a Build.
22. As an Admin, I want an error removing one resource logged and listed in the report while the rest goes on, so that one stuck resource does not block the cleanup.
23. As an operator, I want `WORKER_CLEANUP=false` to turn the automatic Cleanup off, so that I can manage the host myself.
24. As a Member, I do not see the "Clean up" action, since managing the Docker host is for Admins.

## Implementation Decisions

**Installation identity**
- A new singleton table holds the Installation id, a random UUID created on first start. The backend reads it at startup and passes it to the Docker runtime.
- The Docker runtime labels every container, volume and Worker Image it creates with `claude-task.installation=<id>`, next to the existing `claude-task.worker` (and `claude-task.slot`) labels. Docker labels are immutable: existing volumes keep no Installation label, and existing containers get it at their next recreation.
- The Base Image recipe gets a `claude-task.platform` label in each of its stages. Worker Images and the intermediate images of every platform Build inherit it, which is what identifies the untagged images left by platform Builds. The recipe change produces a new Platform Version, so every Worker rebuilds once, as with any platform upgrade.

**Runtime (the only Docker component)**
- `WorkerRuntime` gains:
  - `cleanup(input)`: the Docker part of a Cleanup. The runtime already knows the Installation id (given at construction) and the Platform Version. The input carries whether any Build is running and a function that loads the Installation's known Workers, each with its current image and whether it is building. The runtime calls it after listing Docker's resources, and again right before removing Worker Images, so a Build that started or finished meanwhile is seen. It returns counts per category, an approximate number of reclaimed bytes and the errors.
  - `removeUnusedImages(workerId, keepTag)`: the existing removal of a Worker's older images, now public, so the reconciler can call it after removing stopped containers.
  - `removeSlot(workerId, slot)`: removes the slot's container and its Service Volume.
  - `removeOldBaseImages()`: step 2 below on its own, for the after-Build trigger.
- The Docker `cleanup`, in order:
  1. List the labelled containers, volumes and images first, then load the known Workers, so a Worker created meanwhile is never mistaken for an orphan.
  2. Old Base Images: untag every `claude-task/agent-base` tag other than the current Platform Version, and `latest` when it points elsewhere. Removal is by tag, not forced, so layers still used by a Worker Image stay. Skipped while any Build runs.
  3. Untagged platform images: Docker's image prune limited to dangling images with the `claude-task.platform` label, whichever Installation built them (they hold no data). Skipped while any Build of this Installation runs.
  4. Worker Images of each known Worker that is not building: remove every tag of its repository except its current image, unforced. Docker refuses those a container still uses, and that refusal is not an error.
  5. Orphans: containers, then volumes, then images whose `claude-task.installation` is this Installation's and whose `claude-task.worker` is not a known Worker. Resources without the Installation label are never removed by this step.
  6. Reclaimed bytes: the difference in image layer size before and after (from Docker's disk usage), which already includes the prune, plus the reported size of the removed volumes. Approximate by nature.
- The fake runtime records every `cleanup`, `removeUnusedImages` and `removeSlot` call and returns a scripted report (default: all zeros), so tests can assert what the scheduler asked for.

**Scheduler**
- A new `cleanup(trigger, userId?)` creates a Cleanup record and runs it in the background. While one runs, a new request returns the running one instead of starting another. Steps:
  1. Docker part: `runtime.cleanup`, with the loader of the known Workers.
  2. Slots above the cap: for each Worker, rows whose slot is above the cap, whose container is not up and that have no active Job. Automatic runs only take those idle (counted like the idle stop) for 7 days or more. The step runs in the Worker's reconcile chain, so no reconcile starts the slot meanwhile; each slot is removed with `runtime.removeSlot`, and its record deleted. Jobs keep their slot number and lose their container reference, as the schema already allows.
  3. Worker Volumes: for each Worker, a `volume.cleanup` request carrying the Cleanup id, the ids of the Projects that run on the Worker, plus those with an active Job there, and the ids of every existing Agent. The Worker records the Cleanup id as pending (decrementing the Cleanup it replaces), and the request goes to a connected Runner, and again to every Runner of the Worker that says hello, until an answer clears the marker. The record counts the Worker Volumes still to answer.
  4. The record is marked finished, with the Docker counts, slot count, bytes and errors. Worker Volume answers may arrive later and are added to it.
- Automatic triggers, all skipped when `WORKER_CLEANUP=false`:
  - a Cleanup at `start()` and every 24 hours after that;
  - after each successful Build, the old Base Images step alone;
  - in the reconciler, a container that is not up, not missing, and whose inspected image is not the Worker's current image is removed (`removeContainer`), followed by `removeUnusedImages`. The slot shows as stopped and is created from the current image at its next start, as for a missing container today.
- The existing removal of older Worker Images after a container is created stays unconditional.
- Every change of the Cleanup record is published as `cleanup.updated` on the `workers` topic with the Cleanup id only, since every User follows that topic and the record is for Admins.

**Runner Protocol**
- Backend → Runner: `volume.cleanup` with `requestId` (the Cleanup id), `keepProjects` (ids) and `keepAgents` (ids). No seq and no ack, like `worktree.remove`.
- Runner → Backend: `volume.cleanup.result` with `requestId`, `projects` (Projects whose Bare Clone or Worktree directory was removed), `agentProfiles`, `reclaimedBytes` and `error` (or none).
- The Runner handles it off the read loop, in the same turn as Worktree work, so it waits for Worktree preparation and removal queued before it. In the home it considers only entries whose names are UUIDs: `repos/<uuid>.git`, `worktrees/<uuid>/` and `.claude-agents/<uuid>/`. Anything else, the shared session directory included, is never touched. For a Project not in `keepProjects` it takes the Bare Clone lock, then removes the Bare Clone (its lock file stays, since another Runner may wait on it) and the Project's Worktree directory. For an Agent not in `keepAgents` it removes the Agent Profile. A Project or Agent used by a Job running in that Runner is skipped. Bytes are the summed sizes of the removed files, measured before removal.
- Backend handling: the answer adds its counts and bytes to the Cleanup record it names, when it still exists, and publishes it. Only the answer that clears the Worker's pending marker decrements that record's pending Worker Volumes, so a repeated answer counts once. Unknown ids are ignored.

**Schema**
- `installation`: singleton row with `id` (uuid) and `created_at`.
- `cleanups`: id, trigger (`automatic` or `manual`), requested by (User, nullable, set null when the User is deleted), started at, finished at (nullable), counts (base images, worker images, dangling images, orphan containers, orphan volumes, orphan images, slots, Projects, Agent Profiles), reclaimed bytes (bigint), pending Worker Volumes, errors (text array). The 20 latest records are kept; older ones are deleted when a new Cleanup starts.
- `workers.volume_cleanup_pending`: nullable reference to a Cleanup (set null on delete).

**API (Admins only)**
- `GET /cleanup` → `{ cleanup: Cleanup | null }`, the latest record.
- `POST /cleanup` → `202 { cleanup }`: starts a manual Cleanup, or returns the running one.
- `Cleanup` (in `shared`): id, trigger, requestedBy (`{ id, name }` or null), startedAt, finishedAt, removed counts, reclaimedBytes, volumesPending, errors.

**Web app**
- Workers list header, Admins only: a "Clean up" button next to "New worker". It opens a confirmation dialog listing the categories it removes (the six above, in plain words) and saying that it never touches images, containers or volumes in use or another Installation's data.
- Confirming posts the request and switches the dialog to the live result: running, then the counts that are not zero, the reclaimed space (formatted, marked approximate), Worker Volumes still pending and errors.
- Under the header, Admins see a single line for the last Cleanup: when, automatic or by whom, space freed, and an error count that opens the details. It reloads on `cleanup.updated`.
- The native app is unchanged.

**Configuration**
- `WORKER_CLEANUP` (default `true`). Fixed values: interval 24 hours, slot retention 7 days, 20 records kept.

## Testing Decisions

- **Backend public API with the fake runtime and fake Runners** (most tests, in a new `cleanup.test.ts`, prior art in `workers.test.ts` and `worktree-status.test.ts`):
  - `POST /cleanup` is admin-only, answers 202, calls `runtime.cleanup` with the known Workers, and a second request while it runs returns the same Cleanup;
  - `GET /cleanup` returns the latest record, and `cleanup.updated` is published;
  - slots above the cap: an automatic run keeps one idle less than 7 days and removes one idle longer (`removeSlot` called, row gone, the Worker's containers no longer list it), a manual run removes both, and a busy or running slot is never removed;
  - Worker Volumes: a connected Runner receives `volume.cleanup` with the right `keepProjects` (the Projects on that Worker, not those moved away) and `keepAgents`. Its answer updates the record. A Worker with no Runner gets the request when its Runner connects, and the record's pending count drops after the answer;
  - the reconciler removes a stopped container whose image is outdated and then calls `removeUnusedImages`. It leaves alone a running one, and a stopped one on the current image;
  - `WORKER_CLEANUP=false` makes `start()` run no Cleanup and leaves stopped containers in place, while `POST /cleanup` still works.
- **Runner as a black box** (prior art in the Runner's `stability_test.go` for `worktree.remove`): `volume.cleanup` removes the Bare Clone and Worktrees of an unknown Project and the Profile of an unknown Agent, keeps the kept ones, never touches non-UUID entries or `.claude-shared`, skips a Project used by a running Job, and answers with counts and bytes.
- **Docker runtime**: an opt-in test against a real Docker daemon (skipped without a socket, like the existing Docker tests). Old base tags are untagged. Labelled orphans of an unknown Worker are removed while unlabelled ones and those of known Workers stay. A Worker's unused old images go, while its current image and an image a container uses stay.
- Config parsing of `WORKER_CLEANUP` in the existing config tests.

## Acceptance Criteria

- [x] Every container, volume and Worker Image the backend creates carries the Installation label; the Installation id is stable across restarts.
- [x] The Base Image recipe labels its stages with `claude-task.platform`.
- [x] A Cleanup runs at backend start and every 24 hours, unless `WORKER_CLEANUP=false`.
- [x] Old Base Image tags are removed by every Cleanup and after each successful Build (unless disabled), never while a Build runs.
- [x] Untagged platform images are pruned, never while a Build runs.
- [x] Older Worker Images no container uses are removed, never the current image or that of a Worker being built.
- [x] The reconciler removes a stopped Worker Container on an outdated image; the slot comes back on the current image with its volumes at its next start.
- [x] Slots above the cap are removed with their Service Volume and record after 7 days without a Job (automatic) or at once (manual), never while up or busy.
- [x] Labelled resources of unknown Workers are removed; unlabelled resources never are.
- [x] Worker Volume cleanup removes Bare Clones and Worktree directories of Projects not on the Worker and Profiles of deleted Agents, waits for a Runner when none is connected, and never touches what a running Job uses or non-UUID entries.
- [x] `POST /cleanup` and `GET /cleanup` work for Admins only; a concurrent request joins the running Cleanup; `cleanup.updated` is published.
- [x] The Workers list shows "Clean up" with a confirmation and a live result, and the last Cleanup line, to Admins only.
- [x] Specs updated (Workers, Runner, Clients) and the glossary has **Cleanup**.
- [x] `pnpm typecheck`, `pnpm test` and the Runner tests pass.

## Out of Scope

- Package manager caches, `~/.cache` and unused mise tool versions in Worker Volumes.
- Session transcripts of Tasks that moved or were deleted.
- BuildKit build cache: the platform builds with the classic builder, which keeps its cache as images.
- Anything on the Docker host the platform did not create (other images, other containers, `docker system prune`).
- Disk usage reporting per Worker, a computed preview before a Cleanup, and the action in the native app.
- Configurable interval and retention.

## Further Notes

- The Installation label only protects resources created from now on. Volumes created earlier have no label, so they are only ever removed with their Worker, as today.
- A Project moved back to a Worker after its Bare Clone was removed clones again at its next Job.
- Untagging another Installation's current Base Image on the same host costs that Installation a Base Image rebuild at its next Build, never data. This was accepted.
- The opt-in Docker test of the runtime's Cleanup (`DOCKER_CLEANUP_TEST=1`) needs a Docker daemon; it was not run in the environment that implemented this task.
