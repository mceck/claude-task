# Web and native clients with a live connection

## Specs

- [Clients](../specs/clients.md)

## Problem Statement

The team delegates work to Agents and talks to them through Task conversations. That only works if every person sees the Board, the Timeline and the Agent's output as they change, without reloading, and can act on them from wherever they are. A browser tab left open shows stale cards and misses an Agent's reply; a teammate away from their desk has no way to read a finished Turn, answer an Agent that needs them, or even learn that it does. When several people and Agents change the same Task at once, late HTTP answers and events arriving out of order make a naive client show old values, duplicate Comments or undo someone else's move.

## Solution

Two clients share one backend. The web app, served by the backend itself, covers the whole product: Projects, a drag-and-drop Board, the Task view with its conversation and Timeline, Wikis, Agents and every administration page, in a dark theme by default. The native app, built with Flutter for iOS, Android, macOS, Windows and Linux, focuses on conversations: Projects in a rail, Tasks grouped by Status like chat channels, the full Task conversation, Agent assignment, Wikis, offline reading and Drafts, unread indicators and phone push notifications.

Both clients keep one WebSocket open to the backend, subscribe to the topics they display, and apply the events the backend pushes after each change commits. After any disconnection they resubscribe and refetch instead of replaying missed events. Version and order rules make them correct when requests and events cross, and the backend drops a client that stops reading before its backlog passes 16 MB.

## User Stories

### Real-time layer

1. As a member, I want Board changes made by others, including Agents, to appear without reloading, so that I never act on stale information.
2. As a member, I want new Comments, Revisions and Agent output on a Task to appear live for everyone viewing it, so that the conversation feels like a chat.
3. As a member, I want the Agent's text and Thinking to stream while it writes, so that I can follow its work as it happens.
4. As a member, I want the streamed preview to be replaced by the stored Agent Comment in place, so that nothing flickers or appears twice.

6. As a member, I want an API retry status and the Setup Script output to show while a Turn prepares or retries, so that I understand delays.
7. As a member, I want the Agents list, an Agent's Queue, builds, build logs and Jobs to update live, so that I can watch an Agent without refreshing.
8. As a member, I want my client to recover by itself after a network drop or a server restart, so that I don't have to reload the page.
9. As a member, I want everything I'm looking at to be refetched after a reconnection, so that changes made while I was away still appear.
10. As a member, I want my client to refetch once a subscription is confirmed, so that changes made between loading a view and subscribing aren't lost.
11. As a member, I want to land on the sign-in page when my Login ended or expired while disconnected, so that I'm not stuck in endless reconnection attempts.
12. As an admin, I want deactivating a User or resetting their password to close their live connections, so that access ends immediately.
13. As an operator, I want a client that stops reading to be dropped instead of buffered without limit, so that the backend's memory stays bounded during streaming Turns.
14. As an operator, I want dead connections detected by a heartbeat, so that the backend frees them within about a minute.
15. As an operator, I want WebSocket handshakes from other sites refused, so that another web page can't hijack a User's Login.
16. As a User, I want my following, mute and read state to reach only my own devices, so that my preferences stay private.
17. As an operator, I want events published only after their transaction commits, so that clients never see changes that were rolled back.

## Implementation Decisions

- **Realtime hub (backend).** Keeps one record per connection (User, Login, topics) and an index from topic to connections. Topics: one per Project, one per Task, one per Agent, one per User, plus the Agents list and the Wikis list. A User topic is accepted only for the connection's own User. Subscribe messages list up to 100 topics, are acknowledged with the accepted list, and control messages are capped at 64 KB (larger ones close the connection with `1009`). Invalid JSON or unknown types get an error reply.
- **Publishing.** Domain modules collect events during their transaction and publish them after commit; scheduler and Agent-management code publish directly after their writes. Each event carries the new projection (card, full Task, Comment, Revision, Agent Timeline item, Session, whole Status, Tag or Queue lists). Live Turn text and Thinking deltas, retry status and Setup Script output go on the Task topic and are never stored.
- **Heartbeat and backpressure.** Ping every 30 s, terminate a connection that missed the previous pong. Before each send, terminate a connection with more than 16 MB queued.
- **Login ending.** Ending a Login closes its connections with code `4001`. The handshake is authenticated by the Login cookie and refused when the `Origin` header names another host.
- **Web app state.** TanStack Query holds server data; a separate small store holds Live Turn previews; Drafts live in memory per Task. One live-connection object ref-counts topic subscriptions from mounted views, applies events to the cache and the Live Turn store, refetches each acknowledged topic, marks all queries stale after a reconnection, clears Live Turn previews on disconnection, re-checks the Login on close and stops on `4001`. Backoff: 0.5 s doubling up to 30 s.
- **Web app consistency rules.** Version guard on cards and Tasks across every cached list and view; closed-category filtering per Board list with refetch on Status changes; Timeline items replaced in place or inserted by the server's order key (time, kind, id), older-than-loaded items left for pagination, duplicates across pages shown once; Session events cancel in-flight Session fetches; Session actions refetch; one save at a time per Task, each sending the larger of the seen version and the User's previous save, with pending values overlaid; optimistic Board moves with fractional positions between neighbours and a per-card revert on failure.
- **Web app routing.** React Router with addresses for Projects, Board (Task dialog and closed visibility in the query string), Project settings, Task page by Task Key, Wikis, Agents and Admin pages; a layout gate for the Login check and forced password change. Theme stored per browser and applied by a same-origin script before first paint.
- **Native app structure.** One controller owns the selection, cached data, connection state, Drafts and push handling; an HTTP client (30 s timeout) and a socket client (15 s connect timeout, backoff 1 s doubling up to 32 s) bound to the active profile; a profile store with secure storage for the Login and pending logout and an atomically written cache file per installation and User; a push adapter over Firebase Messaging. Dart models mirror the shared TypeScript shapes the app uses.
- **Native layout.** Breakpoints at 1000 px (three panes) and 1500 px (details panel). Status-grouped Task list with closed-category Tasks behind "Archive".
- **Native live updates.** Subscribes to its User topic, Agents, Wikis, the open Project and the open Task. Timeline events of the open Task merge immediately in the server's order and retire their Live Turn preview in the same update; other events trigger a debounced refresh after 180 ms.
- **Native sending.** Drafts are persisted with an "unknown outcome" flag set before each send; a timeout, lost connection or server error leaves it set and requires "Refresh and review" before the next manual send.
- **Following, read positions and devices (backend contract).** Per-User, per-Task preferences (following, muted, read position, latest position, unread) with automatic following that respects explicit choices; a read-position endpoint that advances monotonically to a persisted Timeline entry; device registration per Login and device id with encrypted tokens; private preference events on the User topic; Timeline responses carry each entry's read position. Push goes through FCM HTTP v1 with generic content, a Task id and per-Task collapse keys, from a durable outbox (rules in the Conversation spec).
- **Create and assign.** Two requests: create the Task, then patch its Agent with the returned version; a failure keeps and opens the Task with "Retry assignment".
- **Conversation generation.** Tasks and Timeline pages carry a generation incremented by Reset Chat; the native app drops cached pages on a mismatch and refetches a page whose generation differs from its Task's, up to two retries.
- **Serving.** The backend serves the built web app from a static folder when it contains the app, with the SPA page for unmatched `GET` requests outside the API, JSON `404` elsewhere, and a Content Security Policy, frame denial, no-sniff and same-origin referrer headers.

## Testing Decisions

- **Backend public API with real Postgres and a WebSocket test client.** Realtime tests cover authentication and origin checks on the handshake, delivery of Board and Task events after commit with their projections, nothing for rolled-back changes or other Projects and Tasks, unsubscribing, fan-out to every subscriber, and dropping a subscriber that stopped reading. Native-support tests cover automatic following and explicit overrides, monotonic read positions, private preference events across WebSocket instances, authentication and CSRF on the new endpoints, push selection and deduplication with a fake transport, rechecks before dispatch, device lifecycle and token takeover, and retries. Static serving has its own test. Wiki tests cover the reset and its event.
- **Web app through Playwright** against the real backend with the fake Agent runtime: login and forced password change; Board creation, drag between and within columns seen live in another browser, closed visibility and combined filters; Comments and Internal Notes seen live elsewhere; image upload and preview; Task page and Board dialog with swappable panels, Draft preservation and live Comments; in-place description editing and image insertion; redirect to sign-in when the Login expired while the WebSocket was down; streaming Turns, Thinking and Activity, Delivery, Stop and Notify agent; Session state kept over a late HTTP snapshot; setup failures and Retry; queue reordering by Members; Wiki creation, two-browser chat and Reset chat for everyone; HTML in descriptions never executed. A concurrency suite holds HTTP responses and WebSocket messages to prove the out-of-order rules: edits to unloaded Comments, out-of-order Timeline events, a failed move with a concurrent creation, quick consecutive Tag toggles, a late save after a live change, typing while sending, and Drafts across dialog closes.
- **Native app through Flutter tests** with a fake API and fake live connection: login and expiry, temporary passwords, Create and assign with partial failure, pagination and the offline cache keeping streamed fragments out, offline Drafts, unknown send outcomes, read advancing only on visible content, notification opening, private preference events and logout cleanup, live updates in place, Timeline order, Wiki conversations and reset detection (live and missed), composer keys and Internal Note switching, native HTTP cookie and CSRF handling, multipart sends, installation URL validation and profile isolation. Widget and golden tests cover phone and desktop layouts of Projects, Task lists and Task description forms, plus the Markdown editor. Native integration smoke tests run on macOS with real storage plugins and a fake API.

## Acceptance Criteria

- [x] Each client keeps one WebSocket, subscribes per topic, and receives events only after the change commits.
- [x] A User topic other than the User's own is refused; preference events reach only that User's connections.
- [x] Handshakes without a Login or from another origin are refused.
- [x] A connection with more than 16 MB queued is terminated, and the client recovers by reconnecting and refetching.
- [x] Clients reconnect with exponential backoff and refetch what they show; a `4001` close leads to sign-in.
- [x] A card moved in one browser appears in another within one second.
- [x] Out-of-order events and late HTTP answers never show an older Task version, a misplaced or duplicated Timeline item, or an older Session state.
- [x] A failed Board move reverts only the moved card.
- [x] Quick consecutive edits of one Task are all saved; a real conflict warns and refreshes.
- [x] Text typed while sending and per-Task Drafts are kept; Drafts are cleared on sign-in and logout.
- [x] Live Turn text, Thinking, retry status and setup output stream and are replaced by stored items without gaps.
- [x] The Wiki section works on web and native, and Reset chat clears the conversation for every viewer.
- [x] HTML in descriptions never runs, and the web app is served with the Content Security Policy.
- [x] The production image serves API, WebSocket and web app, with the app page for client-side addresses.
- [x] The native app signs in to an installation URL, stores the Login in secure storage and isolates cached data per installation and User.
- [x] Narrow windows use successive screens; wide windows show rail, Task list and conversation; details join from 1500 px.
- [x] Tasks are grouped by Status, with search, filters and closed-category Tasks behind a toggle.
- [x] Create and assign keeps the Task and retries only the assignment after a failure.
- [x] Loaded conversations and Drafts work offline; sends are manual; unknown outcomes require reconciliation.
- [x] Unread state is shared across devices and advances only when the latest entry is reached on a visible conversation.
- [x] Following and mute are stored on the backend, explicit choices win over automatic following.
- [x] Push notifications use FCM HTTP v1 with generic content, deduplicated per event and device, and the app reports an unconfigured state honestly.
- [x] Tapping a notification opens the right Task or Wiki after authentication.
- [x] The native app detects a missed Wiki reset through the conversation generation.
- [x] The macOS app builds and passes the native smoke tests; Android debug APK and iOS simulator builds succeed.
- [ ] Phone push is verified end to end on a real iOS and Android device with deployment Firebase and APNs credentials.
- [ ] The app runs on physical iOS and Android phones with distribution signing and the organization's application identifiers.
- [ ] The Windows and Linux apps are built and exercised on their platforms.
- [ ] The backend checks (type checks, the native-support tests and the full suite) pass again after the Flutter SDK migration.

## Out of Scope

- A browser build of the native app, a Board view in the native app, multiple installations or Users at once, voice channels and direct messages.
- Task changes or Comment sends queued offline for automatic submission.
- Administration in the native app: Agents, Credentials, container builds, Git Connections and Project secrets stay in the web app.
- Desktop notifications while the native app is fully closed.
- Unread state and read positions in the web app.
- Replaying missed events after a reconnection.

## Further Notes

- This task records work already built across the web app, the native app and the realtime hub; it depends on the Board, Conversation, Agent sessions and Wikis work those clients display.
- Real phone push requires a Firebase project, a mounted service account on the backend, APNs keys for iOS and the client options passed at build time; the native app's own instructions list the steps.
- The Android release build still uses the development signing key and the scaffold application identifiers until replaced for distribution.
