## Problem Statement

Today an Agent is two things at once: a Claude Code configuration (Credential, model, effort, permission mode, system prompt, environment, Skills, MCP servers, Plugins) and a Docker environment (Dockerfile, Development Services, CPU and memory limits) with exactly one Agent Container and one Agent Volume. That coupling hurts in three ways:

- **Changing Agent loses the conversation.** The Session is per (Task, Agent) and the transcript lives on the old Agent's volume, so moving a Task to another Agent (a different model, a cheaper Credential, other Skills) starts Claude over from the Comments.
- **Throughput means duplicating Agents.** One Agent runs one Job at a time. To work two Tasks in parallel with the same setup an Admin duplicates the Agent, which duplicates its image, volume, services and Queue, and Users have to pick the right copy.
- **Toolchains are configured per Agent, not per kind of work.** Every Agent that needs the same Flutter or Rust toolchain repeats the same Dockerfile and rebuilds the same image.

## Solution

The Docker side of an Agent moves to a new entity, the **Worker**, and the Agent keeps only its Claude Code configuration.

- An Admin creates **Workers**: name, description, Dockerfile, Development Services, CPU and memory limits per container, a **minimum** and a **cap** of Worker Containers (cap from 1 to 20). A Worker autoscales between the minimum and the cap: it starts a Worker Container when work waits and every running one is busy, and stops one that has been idle for 10 minutes, never going under the minimum.
- **Each Project runs on exactly one Worker**, chosen when the Project (or Wiki, or Schedule) is created, by any User. The Worker of a Project can be changed while none of its Sessions is started and open.
- **One Session per Task** (per Chat in a Wiki), independent of the Agent. Changing the Agent of a Task resumes the same Claude conversation with the new Agent's configuration, opened by an Agent Change Notice. The Turn in progress is not interrupted. Removing the Agent still interrupts and pauses.
- **The Queue belongs to the Worker.** Any free Worker Container takes the first ready entry. An Agent has no concurrency limit: the same Agent can work five Tasks at once on five Worker Containers.
- All Worker Containers of a Worker share one **Worker Volume** (Worktrees, Bare Clones, transcripts, mise tools, Agent Profiles), so any of them can resume any Session. Each **Worker Slot** keeps its own **Service Volume** for Development Service data. The dispatcher prefers the slot that last worked the Task.
- Skills and Plugins are installed per Agent into an **Agent Profile** (`CLAUDE_CONFIG_DIR`) inside the Worker Volume, whose transcripts directory is shared by every Agent Profile.
- In a **Wiki**, the Worker and a default Agent belong to the Wiki, and each Chat has its own Agent, changeable from the Chat.
- On upgrade, a migration creates a minimal Worker "Default" and assigns it to every existing Project. A new installation starts with no Worker, and an Admin creates one before the first Project.

## User Stories

### Workers

1. As an Admin, I want to create a Worker with a name, description, Dockerfile, Development Services and CPU and memory limits, so that I configure a toolchain once and reuse it across Projects.
2. As an Admin, I want to set a Worker's cap from 1 to 20, so that I decide how many Tasks of its Projects can run in parallel.
3. As an Admin, I want to set a Worker's minimum from 0 to the cap, so that I can keep one container warm and avoid the start delay on the first reply.
4. As an Admin, I want a Worker with minimum 0 to stop all its containers when there is no work, so that idle environments don't hold CPU, memory and databases.
5. As an Admin, I want the Worker's first Build to start as soon as I create it, so that it is ready by the time someone assigns it to a Project.
6. As an Admin, I want to apply Dockerfile, services and limits together with "Save Docker configuration", so that an unfinished Dockerfile never reaches the running containers.
7. As an Admin, I want name, description, minimum, cap and enabled to save automatically, so that tuning capacity takes no extra click.
8. As an Admin, I want a failed Build to leave the previous image serving, so that a typo in a Dockerfile doesn't stop the Projects running on that Worker.
9. As an Admin, I want each Worker Container to switch to a new image or new limits as soon as it is free, independently of the others, so that a rebuild never interrupts running work and still rolls out quickly.
10. As an Admin, I want lowering the cap to stop the slots above it once they are free, keeping their data, so that raising the cap again reuses their databases.
11. As an Admin, I want to Restart or Force recreate a single Worker Container, and to read its logs, so that I can fix one stuck container without touching the others.
12. As an Admin, I want Rebuild and Recreate when idle to act on the whole Worker, so that I roll out a change everywhere with one action.
13. As an Admin, I want to duplicate a Worker, so that I can start a variant of an existing toolchain.
14. As an Admin, I want to disable a Worker, so that it takes no new Jobs while its Queue keeps accumulating.
15. As an Admin, I want deleting a Worker used by any Project to be refused with the list of those Projects, so that no Project is left without an environment.
16. As an Admin, I want deleting an unused Worker to remove its containers, images, Worker Volume and Service Volumes, so that the Docker host is cleaned up.
17. As a User, I want a Workers list with each Worker's state, busy and running containers, Queue length and Projects, so that I can see where capacity is going.
18. As a User, I want a Worker page with one row per slot (container state, Runner connected, the Task and Agent of its current Job), so that I see what each container is doing.
19. As a User, I want to reorder and remove entries of a Worker's Queue, each showing its Task and Agent, so that urgent work goes first as today.
20. As a User, I want to see a Worker's Builds and their logs live, so that I understand why a Build failed.
21. As a User, I want to see which Projects run on a Worker, so that I know the impact of a change to it.

### Agents

22. As an Admin, I want an Agent to hold only Credential, model, effort, permission mode, system prompt, environment, Skills, MCP servers and Plugins, so that switching Agents never touches Docker.
23. As an Admin, I want a change to an Agent's Extensions to apply on every Worker before that Agent's next Job there, without blocking other Agents, so that a slow Plugin install doesn't stall the whole Worker.
24. As an Admin, I want a failed Extension synchronization to show on the Agent and on the Worker, so that I know which Agent is blocked where.
25. As an Admin, I want to duplicate an Agent's configuration, so that I can create a variant with another model or prompt.
26. As an Admin, I want deleting an Agent to be refused while it is assigned to an open Task, a Chat, a Wiki as default Agent or a Schedule, so that no work is left without an Agent.
27. As a User, I want the Agents list to show each Agent as disabled, idle or working with its number of active Jobs and their Tasks, so that I can see how busy it is.
28. As a User, I want the Agent page to show its active Jobs (with Worker and slot), recent Jobs and usage, so that I can follow its work across Workers.
29. As a User, I want an Agent's past Jobs to keep its name in the history after it is deleted, so that the Timeline and Jobs remain understandable.

### Sessions and Agent changes

30. As a User, I want changing the Agent of a Task to keep the Claude conversation, so that the new Agent remembers everything said and done.
31. As a User, I want the new Agent to be told it now works as itself and who worked before, so that it doesn't get confused by instructions or tools that changed.
32. As a User, I want changing the Agent while a Turn runs to let that Turn finish with the previous Agent, so that work in progress isn't lost.
33. As a User, I want Comments I post after the change to reach the new Agent, not the Turn still running with the old one, so that what I write is read with the configuration I chose.
34. As a User, I want the Stop button to remain available, so that I can stop the old Agent at once when I want to.
35. As a User, I want removing the Agent to interrupt the running Turn and pause the Session, so that the Agent stops working when I take it off.
36. As a User, I want assigning any Agent to a paused Session to resume the same conversation, including the Comments written while it had no Agent, so that nothing gets lost.
37. As a User, I want a pending Limit Resume to survive an Agent change, so that the work resumes after the limit resets.
38. As a User, I want changing the Agent to never start a Job by itself, so that the first Comment stays the trigger and I decide when the new Agent works.

### Queue and concurrency

39. As a User, I want my Comment to start a Job as soon as any container of the Project's Worker is free, so that parallel Tasks don't wait behind each other.
40. As a User, I want my Task to go back to the container that worked it last when that one is free, so that its databases and background processes are still there.
41. As a User, I want two Chats of one Wiki never to run at the same time, since they share one Worktree, so that two Agents never edit the same files in parallel.
42. As a User, I want the Session chip and the Board card to show the position of my Task in its Worker's Queue, so that I know how long I wait.
43. As a User, I want a Task whose Agent is disabled to keep its entry waiting without blocking the other Tasks of the Worker, so that one disabled Agent doesn't stall everyone.

### Projects, Wikis and Schedules

44. As a User, I want to choose the Worker when I create a Project, preselected when only one exists, so that the Project knows where its Agents run.
45. As an Admin on a new installation, I want the Project form to tell me to create a Worker first, with a link, so that I know why I cannot create a Project yet.
46. As a Member on a new installation, I want the Project form to tell me to ask an Admin for a Worker, so that I am not stuck without explanation.
47. As a User, I want to change a Project's Worker from its Agents settings, so that it moves to another toolchain.
48. As a User, I want that change to be refused while the Project has started, open Sessions, with the list of Tasks to close, so that no conversation is stranded on the old Worker's volume.
49. As a User, I want to choose a Wiki's Worker and default Agent at creation and in its settings, so that the Wiki runs where its tools are.
50. As a User, I want each Chat to have its own Agent, the Wiki's default when the Chat starts, and to change it from the Chat, so that I can ask a different Agent in one conversation without losing it.
51. As a User, I want changing the Wiki's default Agent to leave existing Chats as they are, so that ongoing conversations keep their Agent.
52. As a User, I want changing a Wiki's Worker to be refused while it has started Chats, so that their conversations are not stranded; I delete the Chats first.
53. As an Admin, I want to choose the Worker of a Schedule in its form, so that unattended runs use the right toolchain.
54. As an Admin, I want a due Schedule whose Worker is disabled to be skipped with "worker unavailable", so that runs don't pile up on a stopped Worker.

### Agents inside a Worker Container

55. As an Agent, I want my system prompt to tell me that Development Services are shared by the Tasks on the same container and may differ from one Job to the next, so that I recreate the data I need instead of assuming it persists.
56. As an Agent with Board Write Access, I want `list_agents` to order Agents by their active Jobs, so that I pick a less busy one.

### Native apps

57. As an Admin on the native app, I want a Worker sheet with the slots and their state and the actions Rebuild, Restart, Recreate when idle and Force recreate, so that I can manage capacity from my phone.
58. As a User on the native app, I want the Worker pickers in Project creation, Project settings, Wiki creation and settings, and the Agent picker on a Chat, so that I can do on the phone what I do on the web.

### Upgrade

59. As an Admin upgrading, I want every existing Project, Wiki and Schedule assigned to a minimal Worker "Default", so that the installation keeps working right after the upgrade.
60. As an Admin upgrading, I want the old Agent containers, images and volumes left untouched, so that I clean them up myself when I'm sure.
61. As an Admin upgrading, I want a warning in the backend log for obsolete settings (`AGENT_STOP_WHEN_UNUSED`, `AGENT_WIKI_IDLE_MINUTES`, `AGENT_STOP_ON_SHUTDOWN`), so that I update my configuration.

## Implementation Decisions

### Domain model and schema

- **Worker**: id, name (1 to 100 characters, unique ignoring case), description (up to 2,000), Dockerfile (same validation as today's Agent Dockerfile), services (same set and canonical order), CPU limit, memory limit, minimum (0 to cap, default 0), cap (1 to 20, default 1), enabled; bookkeeping moved from the Agent: current image and its Platform Version, image state, pending Build flag, timestamps.
- **Worker Container** (one row per Worker Slot that has ever been started): Worker, slot number (unique together), Runner token hash, the image and limits the container was created with, last observed container state, pending forced recreation flag, Runner connected and disconnected times, Runner and Claude versions, last Job end time (for the idle timeout), last activity.
- **Build**: belongs to a Worker instead of an Agent; otherwise unchanged.
- **Agent Profile synchronization**: one row per (Worker, Agent) with the applied Extensions revision, the error, and an in-progress flag. The Agent keeps its Extensions revision.
- **Agent**: loses Dockerfile, services, limits, Runner token, image, container and synchronization bookkeeping, Runner versions. Keeps identity, Credential, model, effort, permission mode, system prompt, environment, Extensions, enabled.
- **Project**: gains a required Worker. A Wiki Project's default Agent is the Wiki's default Agent. Schedule Projects carry the Schedule's Worker.
- **Session**: unique per Task; no Agent column. It records the Worker Slot and the Agent of its latest Job (for affinity and for the Agent Change Notice).
- **Queue Entry**: belongs to a Worker instead of an Agent; unique per Task.
- **Job**: gains Worker and Worker Slot; keeps the Agent reference (cleared when the Agent is deleted) plus the Agent's name copied at dispatch. The Job's options (model, effort, permission mode, system prompt, environment, MCP) are those of the Task's Agent at dispatch.
- **Turn, Agent Item, rate-limit observation**: keep the Agent reference, cleared when the Agent is deleted.

### Workers API

- `GET /workers`, `GET /workers/:id` for every User; `POST /workers`, `PATCH /workers/:id`, `DELETE /workers/:id`, `POST /workers/:id/duplicate`, `POST /workers/:id/rebuild`, `POST /workers/:id/recreate` (when idle, every container) for Admins.
- Per container, Admins: `POST /workers/:id/containers/:slot/restart`, `POST /workers/:id/containers/:slot/force-recreate`, `GET /workers/:id/containers/:slot/logs` (1 to 5,000 lines).
- Builds and logs: `GET /workers/:id/builds`, `GET /workers/:id/builds/:buildId/log`, every User.
- Queue: `GET /workers/:id/queue`, reorder and remove entries, every User (moved from the Agent routes, same semantics).
- `DELETE` answers `409` naming the Projects (any kind, archived included) that use the Worker. A deletion removes Builds, Worker Container rows and synchronization rows, then the containers, images, Worker Volume and Service Volumes in the background.
- Duplicate copies every configuration field with the "‹name› (copy)" naming rule, gets its own Build and an empty Worker Volume, and starts disabled only if the source is disabled.
- Real-time: a `workers` topic (list) and a `worker:<id>` topic (Worker, containers, Queue, Builds and log chunks). The Agent topic keeps the Agent and its Jobs; the Agent Queue events move to the Worker topic.

### Agents API

- Docker fields, container actions, Build routes and Queue routes leave the Agent API.
- Agent deletion answers `409` while the Agent is assigned to any Task not in a `closed`-category Status (Wiki Chats included), is the default Agent of a Wiki, or is the Agent of a Schedule, naming them. A Project whose default Agent is deleted gets no default Agent. Closed Tasks still assigned are unassigned with a Revision, as today. Sessions, Jobs, Turns, Agent Items and events stay; their Agent reference is cleared and the Job keeps the copied name. Agent Profiles stay in the Worker Volumes until the Worker is deleted.
- Agent State: `disabled`, else `working` with the count and Tasks of its active Jobs, else `idle`.
- `list_agents` (Board Write Access) orders enabled Agents by number of active Jobs, then name, and answers each Agent's state, active Job count and current Tasks.

### Projects, Wikis and Schedules API

- Project creation requires `workerId` (an existing Worker; `400` otherwise). The Agents settings section gains the Worker picker (every User). Changing it answers `409` listing the Tasks while any Session of the Project is started and not `closed` or any Job of the Project is active. When allowed, the Project's Queue Entries move to the new Worker's Queue in the same transaction, keeping their relative order at the end of the new Queue.
- Wiki creation requires a Worker and a default Agent; Wiki settings edit both, with the same `409` rule for the Worker (started Chats block it; Delete Chat makes a Chat not started). The Chats API gains a way to change a Chat's Agent (any User, any existing Agent, required: a Chat always has an Agent). New Chat sets the empty Task's Agent to the Wiki's default Agent.
- The "this Chat belongs to Agent X" `409` and the pausing and unpausing of Chats on a Wiki Agent change are removed.
- Schedules gain a required Worker (Admins), with the `409` rule for changes. The skip check adds "worker unavailable" when the Worker is disabled.
- Clients: when no Worker exists, Project, Wiki and Schedule forms show "Create a Worker first" with a link for Admins, and "Ask an Admin to create a Worker" for Members. The picker preselects the Worker when exactly one exists.

### Session lifecycle

- One Session per Task, created `pending` on the first Assignment, kept for the Task's whole life.
- **Changing the Agent (A to B)** on a Session that is not `closed`: the Session keeps its state (a `paused` one returns to `idle` or `pending` as below). An active Job continues and is not interrupted. From the change on, Comments for the Task are queued instead of written to the running Job, whose Agent is no longer the Task's. Queued Comments stay in the Task's entry. Nothing is queued by the change itself. The pending Limit Resume stays.
- **Agent Change Notice**: at dispatch, when the Session is started and the Task's Agent differs from the Agent of the Session's latest Job, the Message opens with: "You are now working as agent "B" (previously "A"). Your instructions, tools and skills may have changed; the conversation so far is preserved." A new Session (never started) receives no notice: its opening Message already introduces the Task.
- **Removing the Agent**: as today. Interrupt plus end of a running Job, entry removed, Comments `not delivered` "agent unassigned", Session `paused`, Limit Resume cancelled.
- **Assigning an Agent to a `paused` Session**: `idle` when started, `pending` otherwise. When started, a `messages` entry is queued with the non-internal, non-deleted User and Agent Comments posted after the last dispatch, if any (they become `queued` again). Without such Comments nothing is queued. The previous "You have been assigned to this task again" notice is replaced by the Agent Change Notice rule.
- The whole "different Agent" branch of reassignment (moving Comments between Agents' Sessions, the "another Agent worked on the Task before" line, reactivating earlier Sessions) is removed.
- Closing, reopening, Delete Chat, Notify agent and recovery work on the single Session.

### Queue and dispatch

- One Queue per Worker, fractional positions, at most one entry per Task, every change under the Worker's row lock. Front-of-Queue rules as today, keyed on "the Task has an active Job".
- An entry is **ready** when it is not held, the Task's Agent is enabled, and no active Job of the Worker uses the same Worktree path (Chats of one Wiki share it). Entries that are not ready are skipped without being held.
- A Worker Container can take a Job when its container runs with the current image and limits, its Runner is connected, it has no Job in `dispatched`, `running` or `finishing`, no recreation is pending for it, it is not being stopped, and the Worker is enabled.
- The dispatcher runs per Worker. For each ready entry in Queue order, it checks the (Worker, Agent) synchronization: when it is out of date, it starts a synchronization (when none runs and the Agent has no active Job on the Worker) and skips the entry. Otherwise it picks the Worker Container by this order: the Session's last slot if free; another free running slot, lowest number first; none (the reconciler scales up). One transaction per Job, as today.
- Every trigger that dispatched an Agent now dispatches the Worker of the Task's Project.

### Autoscaling and the reconciler

- The reconciler runs per Worker, serialized, at startup, every 30 seconds, after Builds, after each Job ends, on Runner connect and after configuration changes.
- **Desired running slots**: every slot from 1 to the minimum while the Worker is enabled, whatever `WORKER_STOP_WHEN_UNUSED` says (the setting only turns off the idle stop, decided while implementing); plus, while ready entries outnumber free running slots, one more slot per waiting entry up to the cap. Entries waiting for a synchronization count as ready. A new slot is the affine slot of the first waiting entry when it is free to start, otherwise the lowest-numbered stopped slot within the cap.
- **Stopping**: a slot above the minimum whose container has had no Job for `WORKER_IDLE_MINUTES` (default 10) since its last Job ended or its Runner connected is stopped, under the Worker's row lock with a recheck, so no Job is dispatched to a container being stopped. Slots above the cap stop as soon as they are free. With `WORKER_STOP_WHEN_UNUSED=false` running containers are never stopped for idleness and no slot is started beyond the minimum and what work needs.
- A disabled Worker starts no slot; its running slots stop after the idle timeout, the minimum ignored.
- Stopping keeps the container; a pending recreation applies at the next start. Restart, Recreate when idle and Force recreate keep today's semantics, per container. A Restart of a stopped container answers `409`.
- Platform upgrades rebuild every Worker whose image is on an older Platform Version.
- Backend shutdown stops every Worker Container when `WORKER_STOP_ON_SHUTDOWN` is enabled (same defaults as today's setting).

### Docker runtime

- Container name `claude-task-worker-‹worker id›-‹slot›`, labels with the Worker id and the slot. Worker Volume `claude-task-worker-‹worker id›`, mounted as the agent user's home. Service Volume `claude-task-worker-‹worker id›-services-‹slot›`, mounted at a fixed path outside the home.
- The entrypoint keeps every Development Service's data and logs in the Service Volume and removes stale locks there, as it does today in the home. The Git credential socket, the Runner's lock files and anything else per-container move to a container-local directory outside the Worker Volume.
- Each container receives the Runner URL and its own Runner token. One Runner connection per Worker Container in the Runner hub; a token maps to one (Worker, slot).
- The fake runtime simulates several containers per Worker and exposes each container's token to the test harness.

### Agent Profiles and Extension synchronization

- Every Job runs with `CLAUDE_CONFIG_DIR` set to the Agent Profile `~/.claude-agents/‹agent id›/`, sent by the backend in the Job's start message. `CLAUDE_CONFIG_DIR` joins the reserved environment names.
- Inside each Agent Profile, `projects`, `todos`, `file-history`, `session-env` and `shell-snapshots` are symbolic links to a shared directory of the Worker Volume, so a Session's transcript and its session data are the same for every Agent.
- Synchronization for (Worker, Agent) runs through `docker exec` in one running Worker Container of the Worker, when the Agent has no active Job on that Worker. It creates the Agent Profile and its links, writes the Skills snapshot and links into the profile's `skills` directory, and installs, updates and uninstalls Plugins with the plugin manager using that profile. A Worker Container recreation does not require a new synchronization, since the profiles live on the Worker Volume.
- The Agent's Extensions revision increments as today; every (Worker, Agent) row whose applied revision is older is out of date. A (Worker, Agent) pair with no row is out of date. Errors are stored per pair and shown on the Agent page and the Worker page.

### Runner

- `job.start` gains the Agent Profile path; the Runner sets `CLAUDE_CONFIG_DIR` for `claude` and validates that the path lies inside the home.
- The Runner holds an exclusive file lock per Bare Clone, in the Worker Volume next to the clone, around every git command that touches it (fetch, worktree add, remove, prune), so two Worker Containers never update a clone at once.
- `worktree.remove` is sent once the Session has no active Job, to a connected Runner of the Worker (the Session's last slot first); it stays pending until one connects. `project_skills.request` goes to any connected Runner of the Worker.
- The outbox spill files go to a container-local directory.
- Protocol version bumps to 4.

### System prompt

- The Development Services paragraph reads that the services run in the current Worker Container, are shared with the other Tasks that run there, and that a later Job of the same Task can run in another Worker Container with different data, so the Agent creates what it needs and keeps Projects apart by database names, key prefixes or buckets.

### Migration

- One database migration. When at least one Project exists, it creates a Worker "Default" (Dockerfile `FROM claude-task/agent-base` and `USER agent`, PostgreSQL and Redis, no limits, minimum 0, cap 1, enabled) and assigns it to every Project of every kind. An empty database gets no Worker.
- Sessions collapse to one per Task: the Task's current Session is kept; Jobs, Turns and Agent Items of the others are attached to it, their Queue Entries are removed (their Comments become `not delivered`, "agent unassigned", which is acceptable since boards are empty at upgrade) and the others are deleted. Every Session is marked not started with its Claude session identity reset, since no transcript is reachable on the new Worker Volume. `running` Sessions become `pending`, active Jobs `interrupted`. Queue Entries move to the Queue of the Task's Project's Worker as `start` entries.
- Agent Docker columns, Agent Builds and Agent runtime bookkeeping are dropped. The migration and the backend perform no Docker operation on old Agent containers, images or volumes; their Runners get `401`.
- At startup the backend logs a warning for each obsolete setting that is set: `AGENT_STOP_WHEN_UNUSED`, `AGENT_WIKI_IDLE_MINUTES`, `AGENT_STOP_ON_SHUTDOWN`, naming its replacement.

### Clients

- Web: a Workers section next to Agents, with the list and a Worker page with tabs **Containers**, **Queue**, **Builds**, **Configuration** and **Projects**, plus the Admin actions. The Agent page loses Docker configuration, Builds, container logs, container actions and the Queue; it shows active Jobs (Task, Worker, slot), recent Jobs and Usage. Project creation and Project settings gain the Worker picker; Wiki creation and settings gain Worker and default Agent; the Wiki Chat header gains the Chat's Agent selector; the Schedule form gains the Worker.
- Native app: a Workers entry in Settings with a Worker sheet (slots and state; Rebuild, Restart per slot, Recreate when idle, Force recreate per slot for Admins); Worker pickers in Project creation and settings, Wiki creation and settings, Schedule form; the Chat Agent selector. The Agent sheet keeps the configuration only.
- Agent pickers keep the Agent state dot; Worker pickers show the Worker State dot with the same palette.

## Testing Decisions

- **Seam 1, backend public API** (HTTP, WebSocket, MCP) against real Postgres, with the fake runtime and fake Runners, one per Worker Container token. Most tests live here. Prior art: `agents.test.ts`, `agent-idle-stop.test.ts`, `sessions.test.ts`, `extensions.test.ts`, `wikis.test.ts`, `schedules.test.ts`, `shutdown.test.ts`, `migrations.test.ts`. Covered:
  - Worker CRUD, validation, permissions, duplicate, delete `409` and cleanup calls on the fake runtime;
  - Builds per Worker and recreation per container when free;
  - autoscaling: scale-up to the cap with parallel Jobs, affinity order, idle stop after the timeout (injectable clock), the minimum always running, cap decrease, disabled Worker, `WORKER_STOP_WHEN_UNUSED=false`;
  - one Job per Worker Container, per Session and per Worktree (two Wiki Chats never run together), Agent without concurrency limit;
  - Agent change: no interrupt, Comments queued after the change, Agent Change Notice at the next dispatch with the new Agent's options in `job.start`, no Job started by the change, Limit Resume kept;
  - unassign and reassign on the single Session, including Comments queued again;
  - Extension synchronization per (Worker, Agent): blocks only that Agent's entries, error per pair, no resync after recreation, Agent Profile path in `job.start`;
  - Project, Wiki and Schedule Worker selection, `409` on change with started Sessions, entries moving to the new Worker's Queue, Wiki Chat Agent change, "worker unavailable" skip;
  - Agent deletion rules and history kept with the copied name;
  - migration from a database with Agents, multiple Sessions per Task and queued entries, and from an empty database.
- **Seam 2, Runner black box**: the Go binary against the fake backend WebSocket, the fake `claude` and a local bare repository. ## Acceptance Criteria

- [x] Workers can be created, edited (auto-save and "Save Docker configuration"), duplicated, disabled and deleted by Admins, with the validation and `409` rules above; every User can read them.
- [x] A Worker builds its image on creation and on Dockerfile or service changes; a failed Build keeps the previous image serving.
- [x] A Worker runs up to its cap of Worker Containers in parallel, keeps slots 1 to the minimum running, and stops an idle slot above the minimum after `WORKER_IDLE_MINUTES`.
- [x] Each Worker Container has its own Runner token and connection, and runs at most one Job.
- [x] The dispatcher prefers the Session's last slot, then another free slot, then starts a slot, in that order.
- [x] Two Chats of one Wiki never have Jobs at the same time; the same Agent can have Jobs on several Worker Containers.
- [x] All Worker Containers of a Worker share the Worker Volume and each slot has its own Service Volume.
- [x] Every Job runs with the Agent Profile of the Task's Agent, and a Session started by one Agent resumes with `--resume` under another.
- [x] Extension synchronization runs per (Worker, Agent) and holds only that Agent's entries on that Worker.
- [x] There is one Session per Task; changing the Agent never interrupts, never starts a Job, and the next Job opens with the Agent Change Notice.
- [x] Removing the Agent interrupts the running Turn and pauses the Session; assigning any Agent resumes it.
- [x] Every Project, Wiki and Schedule has a Worker, chosen at creation; changing it is refused with `409` while started, open Sessions exist.
- [x] Each Wiki Chat has its own Agent, defaulting to the Wiki's default Agent, changeable from the Chat in both clients.
- [x] The Queue lives on the Worker, is shown and reordered on the Worker page, and the Session chip shows the position in it.
- [x] Agent deletion follows the new rules and keeps the Agent's name on its past Jobs.
- [x] The Base Branch Push Policy, Job token scope and secrets-per-Job rules hold unchanged.
- [x] The migration assigns a "Default" Worker to every existing Project, keeps one Session per Task and touches no Docker resource; a fresh database has no Worker.
- [x] Web and native clients offer the Worker pages, sheets and pickers described above.
- [x] `CLAUDE.md` invariants, `docs/CONTEXT.md` and the listed specs describe the new model.
- [x] `pnpm typecheck`, `pnpm test`, the Runner tests and `pnpm test:e2e` pass, except three e2e tests that fail the same way on `main` (board image insert, muted badges, skill assignment). The opt-in real-Docker entrypoint test was written but not run (no Docker daemon available).

## Out of Scope

- A concurrency cap per Agent or per Credential.
- Workers on remote Docker hosts or Kubernetes.
- Copying Sessions between Worker Volumes when a Project changes Worker.
- Removing old Agent containers, images and volumes (left to the Admin).
- A per-Task choice of Worker.
