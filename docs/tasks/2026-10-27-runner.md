# Runner

## Specs

- [Runner](../specs/runner.md)

## Problem Statement

Agents work on Tasks inside long-lived Agent Containers, but the backend owns the Queue, the Sessions and the Jobs. Something inside each container has to carry out the Jobs the backend decides: prepare the Task's Worktree, run `claude` headless, feed it the Comments people write (even mid-turn), and bring every line of its output back to the Task. It must survive dropped connections and container restarts without losing output, keep secrets away from the Agent's own tools, give git credentials for the Git Proxy without putting provider tokens in the container, and stay robust when setup scripts hang, tools leave background processes behind, output lines are huge or a Task is closed in the middle of work.

## Solution

A small static Go binary, the Runner, is the main process of every Agent Container. It dials out to the backend over one authenticated WebSocket and speaks the Runner Protocol: it receives `job.start`, `job.input`, `job.interrupt`, `job.end`, `job.cancel`, `worktree.remove`, `ack` and `ping`, and sends `hello`, Job-scoped messages with a per-Job seq, and `pong`. For each Job it prepares the Worktree (git steps, tool install, Setup Script, attachments), starts `claude -p --input-format stream-json --output-format stream-json` in it, writes Messages to stdin, forwards stdout lines verbatim, and reports the exit. Unacknowledged messages are kept and resent after a reconnect. A Git credential helper shipped with it answers git with the current Job's token, only for that Job's Git Proxy URL.

## User Stories

1. As an admin, I want the Runner to connect out to the backend, so that Agent Containers expose no ports.
2. As an admin, I want the Runner to authenticate with a Runner token that maps to exactly one Agent, so that a container can act only for its own Agent.
3. As an admin, I want a new Runner connection for an Agent to replace the previous one, so that a restarted Runner takes over cleanly.
4. As an admin, I want the Runner to reconnect automatically with exponential backoff and jitter, so that a backend restart doesn't need manual action and Runners don't stampede it.
5. As an admin, I want both sides to send heartbeats, so that a half-open connection is detected and its Job recovered.
6. As an admin, I want the Runner to report its protocol version, its own version and the `claude` version on connect, so that I can see what each Agent runs.
7. As a member, I want a Job to keep running while the backend connection is down, so that a short outage doesn't stop the Agent.
8. As a member, I want every output line produced during a disconnect to reach the Task once the connection is back, so that the Timeline has no gaps.
9. As a member, I want each output line processed exactly once and in order, so that the Timeline has no duplicates.
10. As an admin, I want unacknowledged output to spill to the Agent Volume past a memory budget, so that a long disconnect can't exhaust the container's memory.
11. As a member, I want the Runner to run one Job at a time, so that Agents never work on two Tasks at once.
12. As a member, I want the next Job sent right after a cancel to wait for the cancelled one to stop, so that closing a Task doesn't make the next Task fail.
13. As a member, I want the Task's Worktree prepared on its Task Branch before `claude` starts, so that the Agent can start working immediately.
14. As a member, I want an existing Worktree left untouched, so that uncommitted work from earlier Turns survives.
15. As a member, I want a Worktree recreated from the remote Task Branch when it exists, or from the latest Base Branch otherwise, so that reopened Tasks continue from their pushed work.
16. As a member, I want a bare clone that belongs to a different Repository discarded, so that a Project switching Repository never reuses old branch commits.
17. As an admin, I want existing clones adopted when their origin moves to the Git Proxy, so that Worktrees and Sessions keep working across the switch.
18. As a member, I want the declared tool versions installed with mise before the Setup Script, so that the project's runtimes are available.
19. As a member, I want the Project's Setup Script run in a new Worktree, so that dependencies are installed before the Agent starts.
20. As a member, I want a Setup Script that failed to run again on Retry, and a successful one to run only once, so that a broken setup can be fixed without recreating anything.
21. As a member, I want setup output streamed live to the Task, so that I can follow and debug preparation.
22. As a member, I want a hanging Setup Script to time out and fail the Job, so that an Agent isn't stuck forever.
23. As a member, I want a Setup Script that leaves background processes behind to still finish, so that a stray server doesn't hang the Job.
24. As a member, I want preparation failures reported with their stage (worktree, setup, spawn) and message, so that I know what to fix.
25. As a member, I want attachments of my Comments downloaded into the Worktree, so that the Agent can read files I shared.
26. As a member, I want a failed attachment download reported without stopping the Job, so that one bad file doesn't block the work.
27. As a member, I want `claude` started with the Session id for a new Session and `--resume` for an existing one, so that each Task keeps one continuous conversation.
28. As a member, I want the Agent's model, effort, permission mode, system prompt and MCP configuration applied, so that the Agent behaves as configured.
29. As a member, I want the repository's CLAUDE.md, `.claude/` settings, skills and `.mcp.json` loaded, so that the Agent follows the repository's conventions.
30. As a member, I want the Project env and the Credential given to `claude` per Job, so that rotations apply at the next Job and secrets stay scoped to their Project.
31. As a member, I want a resumed interrupted Turn to continue on its own, so that a container crash doesn't lose the Turn.
32. As a member, I want my Comment written to `claude`'s stdin while it works, so that I can steer it mid-turn.
33. As a member, I want Comments sent before `claude` has started applied in order after the initial Message, so that nothing is lost during preparation.
34. As a member, I want Stop to end the current Turn and keep the process, so that I can redirect the Agent with my next Comment.
35. As a member, I want the end of a Turn to let `claude` finish the Messages already written before it exits, so that late input is still handled.
36. As a member, I want closing a Task to cancel its Job with interrupt, then SIGTERM, then SIGKILL, so that even a stuck process stops.
37. As a member, I want a cancel during the Setup Script to stop it at once, so that closed Tasks release the Agent quickly.
38. As a member, I want every stdout line forwarded verbatim and each `result` reported as the end of a Turn, so that the backend can project the Timeline and end the Job.
39. As an admin, I want an oversized stdout line replaced by a placeholder with its beginning and size, so that one huge line doesn't break the connection forever.
40. As a member, I want stderr forwarded for diagnostics, so that crashes and CLI refusals can be explained.
41. As a member, I want output chunks never to split a UTF-8 character, so that non-ASCII output shows correctly.
42. As a member, I want an input that arrives after stdin closed reported, so that a lost Message is visible in the Job's diagnostics.
43. As a member, I want background processes started by the Agent's tools killed when `claude` exits, so that they don't hold ports and files into the next Job.
44. As a member, I want output written just before `claude` exits still forwarded, so that the end of a Turn isn't lost.
45. As a member, I want the exit code or signal reported, so that crashes are distinguishable from clean exits.
46. As an admin, I want a closed Task's Worktree removed while its branches stay, so that Agent Volumes don't grow forever.
47. As an admin, I want a Worktree removal to wait for the Jobs still using it without blocking the connection, so that closing a Task is safe and the Runner stays responsive.
48. As an admin, I want Worktree preparation and removal handled in the order they were requested, so that reopening a Task right after closing it works.
49. As an admin, I want Worktree, bare clone and attachment paths confined to the Agent's home and the Worktree, so that a malformed message can't touch other files.
50. As an agent, I want `git fetch`, `pull` and `push` to work without handling credentials, so that I can use git normally.
51. As an admin, I want the Git credential helper to hand out the Job token only for the current Job's exact Git Proxy URL, so that no other host or path gets it.
52. As an admin, I want git to persist no credential, so that tokens never land on disk.
53. As an admin, I want the Runner token kept out of every process the Runner starts, of the container's first process, of the services and of backend execs, so that the Agent's tools can't read it.
54. As an admin, I want the Runner's memory unreadable by other processes of the same user, so that the Runner token and Job secrets stay private.
55. As an admin, I want the Runner to forward a container stop to `claude` and exit promptly, so that container recreation is quick and the backend can resume the interrupted Turn.
56. As a developer, I want the `claude` path, cancel delays, setup timeout and outbox budget configurable, so that the Runner can be tested with a fake CLI and short timings.

## Implementation Decisions

- The Runner is a static Go binary, built locally by the backend into the Base Image together with the Git credential helper. The entrypoint starts the selected development services, then the Runner, as the `agent` user.
- The Runner Protocol is JSON over one WebSocket, authenticated with the Runner token as a bearer header. The shared TypeScript types are the source of truth and the Go types mirror them. Protocol version 2 (the Git Proxy version) dropped the Runner's git token request and reply.
- `job.start` carries the Job id, the session id, the mode (`new` or `resume`), the resume-interrupted flag, the Worktree path, an optional git spec (Git Proxy clone URL, Job token, Repository identity, Base Branch, Task Branch, a remote-branch hint, the bare clone path, the commit identity), the Setup Script, the merged environment, the Claude arguments (model, effort, permission mode, appended system prompt, MCP configuration), the initial Message and the attachments to fetch.
- Runner to backend: `hello` (protocol version, Runner version, `claude` version, active Job), then per Job `job.accepted`, `job.worktree_ready`, `job.setup_output`, `job.event`, `job.result` (with the seq of its `result` event), `job.stderr`, and finally `job.exited` or `job.failed` (stage `worktree`, `setup` or `spawn`). `pong` answers `ping`.
- One seq counter per Job, shared by every Job-scoped message type. The backend acknowledges cumulatively after processing each message, skips seqs it already processed, and acknowledges messages for unknown Jobs without effect.
- On connect the Runner sends `hello`, then resends every unacknowledged message, oldest Job first, before new sends. On `hello` the backend acknowledges up to its last processed seq for the active Job, cancels a Job it already settled, and recovers every other active Job as interrupted.
- The outbox keeps 50 MiB in memory per Job and spills the rest to a file on the Agent Volume, deleted when the outbox empties. A Job is forgotten once finished and fully acknowledged.
- Reconnect backoff starts at 1 s, doubles to 30 s, with a random wait between half and all of it, and resets after an established connection. Dial timeout 15 s, write timeout 10 s, Runner WebSocket ping every 30 s with 15 s to answer. The backend pings every 30 s (frame and JSON) and drops a Runner silent for a whole interval.
- Incoming messages up to 64 MiB; outgoing messages capped at 32 MiB, half the backend's 64 MiB limit. A stdout line over the cap becomes an `unparsed` placeholder with its first 16 KiB and its size; a leading `result` type still triggers `job.result`.
- One Job at a time: a duplicate `job.start` is ignored; a `job.start` during a cancel waits up to the kill delay plus 5 s; otherwise a second Job fails at stage `spawn` with "another job is running".
- Worktree preparation and removal go through one ordered line. Removal runs off the read loop and waits for unfinished Jobs on that Worktree.
- Git steps: discard a bare clone recorded for a different Repository identity (a clone without identity is adopted), create or update the bare clone with the Git Proxy as origin, record the identity, fetch with prune, keep a valid Worktree, else recreate it with a forced local Task Branch from the remote Task Branch or the Base Branch and set its upstream by config, set the commit identity, exclude the platform directory. Each git command has 30 minutes, prompts disabled.
- A new Worktree gets a setup-pending mark as soon as it exists. mise install runs (Jobs with a Repository and a mise config) when the Worktree was created, is still pending, or the Job starts a new session. The Setup Script runs with `bash -lc` when the mark is present, and the mark is removed on success.
- Every child (setup step or `claude`) runs in its own process group. Setup steps have a 30-minute limit each, stream output through a pipe, and have their group killed when they end.
- `claude` arguments: `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages`, `--session-id` or `--resume`, and `--model`, `--effort`, `--permission-mode`, `--append-system-prompt`, `--mcp-config` when set. Never `--bare`. Working directory: the Worktree.
- Environment of every child: the Runner's environment without the Runner token and backend URL, plus the Job's environment (Project env, Credential variable, resume flag).
- `job.input` downloads its attachments then writes one stream-json user message. `job.interrupt` writes a `control_request` interrupt, with SIGINT as fallback once stdin is closed. `job.end` closes stdin. `job.cancel` interrupts and closes stdin, SIGTERM at 10 s, SIGKILL at 20 s; during a setup step, SIGTERM at once.
- After `claude` exits, its process group is killed, output pipes drain until 2 s of silence (1 minute at most), then `job.exited` reports the exit code or signal name. The Job is marked finished as its last message is sent, so an immediate next `job.start` is accepted.
- Output chunks are at most 64 KiB and end on whole UTF-8 characters.
- Attachments are downloaded with the Runner token, 5 minutes each, through a temporary file; failures go to stderr as Runner notes.
- Git credential helper: configured system-wide with the request path; `get` validates the request and asks the Runner over a 0600 Unix socket (3 s connect, 40 s exchange); `store` and `erase` do nothing. The Runner answers username `claude-task` and the Job token for the current unfinished Job when scheme, host, port and path (ignoring a leading slash and trailing `.git`) match its clone URL, and "no active task for this repository" otherwise.
- Runner token secrecy: the entrypoint re-executes without the token and passes it to the Runner over a pipe; backend execs blank it; the Runner removes it from its environment at start and marks itself non-dumpable on Linux.
- On SIGTERM or SIGINT the Runner sends SIGTERM to the running group, SIGKILL after 5 s, and exits.

## Testing Decisions

- Seam: the Runner as a black box. The real Go binary runs as a subprocess against a fake backend WebSocket server, with a fake `claude` executable (a small Go program that reads stream-json, emits scripted responses, records its arguments, environment, working directory and stdin, honours interrupt, and can hang, ignore SIGTERM, spawn background processes or trickle output) and a local bare git repository as origin.
- Protocol and process tests cover: hello and arguments for a new session, resume and a reused session id, mid-turn input reaching the running Turn, messages before spawn applied in order, interrupt keeping the process, cancel escalating to SIGTERM and SIGKILL, resend after a backend disconnect (in memory and spilled to disk), one Job at a time, the Setup Script only for a new Worktree, the Runner token kept out of Job processes, paths confined to the home, attachments fetched into the Worktree.
- Git tests cover: a new Task Branch, an existing remote Task Branch, later Jobs fetching and keeping the Worktree with uncommitted work, removal keeping branches, a deleted remote Task Branch recreated from the latest base, a changed Repository discarding old commits, origin moving to the Git Proxy keeping clones and Worktrees, a changed Repository behind the same proxy URL, mise install before the Setup Script, a mise failure stopping `claude` and being retried, git hooks running without the Runner token.
- Credential tests cover: the helper serving the token only for the active Job's exact proxy URL, denying after the Job ends and serving the next Job's own token, denying a Job without a token, and `store` needing no socket.
- Stability tests cover: a Setup Script background process not hanging the Job, cancel stopping the Setup Script, the Setup Script timeout, Runner credentials out of child processes, the oversized-line placeholder, Worktree removal not blocking the connection and waiting for a running Job, a `job.start` waiting for a cancelled Job, the next Job right after an exit being accepted, a failed setup running again on Retry, setup after a failed preparation of a new Worktree, multibyte output never split, undeliverable input reported, background processes ending with `claude`, and output after exit forwarded.
- The backend side of the protocol is covered in the backend suite with a fake Runner; an opt-in real-Docker test checks that the entrypoint keeps the Runner token out of the container's first process.

## Acceptance Criteria

- [x] The Runner connects with its Runner token, sends `hello` with protocol, Runner and `claude` versions and its active Job, and reconnects with backoff after a disconnect.
- [x] Every Job-scoped message carries a per-Job seq; unacknowledged messages are resent after a reconnect and spill to the Agent Volume past the memory budget.
- [x] The Runner runs one Job at a time; a second `job.start` fails at stage `spawn` unless the running Job is being cancelled, in which case it waits.
- [x] The Worktree is prepared on the Task Branch; an existing Worktree with uncommitted changes is left untouched; branches survive Worktree removal.
- [x] mise install and the Setup Script run before `claude` for a new Worktree, stream their output, time out after 30 minutes, and run again on Retry after a failure.
- [x] `claude` runs in the Worktree with the stream-json flags, `--session-id` or `--resume`, the configured model, effort, permission mode, system prompt and MCP configuration, and the Job's environment.
- [x] A `job.input` during a Turn reaches `claude`'s stdin and is handled within that Turn.
- [x] `job.interrupt` ends the Turn and keeps the process; `job.end` closes stdin and lets queued Messages finish; `job.cancel` escalates to SIGTERM at 10 s and SIGKILL at 20 s.
- [x] Every stdout line is forwarded verbatim, followed by `job.result` for `result` lines; oversized lines become a placeholder.
- [x] `job.exited` reports the exit code or signal after all output written before the exit, and background processes end with `claude`.
- [x] Preparation failures are reported as `job.failed` with stage and message, and `claude` doesn't start after one.
- [x] The Git credential helper returns the Job token only for the current Job's exact Git Proxy URL and denies everything else, including when idle.
- [x] No provider token exists in the container, and the Runner token is absent from every process the Runner starts, from the container's first process and from backend execs.
- [x] Worktree, bare clone and attachment paths that escape their base fail or are skipped.
- [ ] The opt-in end-to-end smoke with real Docker and the real `claude` CLI runs a full Job (preparation, Turns, mid-turn Message, push through the Git Proxy).

## Out of Scope

- Running several Jobs at once in one Agent Container.
- A live terminal into the Agent Container.
- Interactive permission approval: the permission mode is fixed per Agent.
- Claude Code hooks: the Timeline comes from the stdout stream.
- Persisting the outbox across Runner restarts: the backend recovers the Job as interrupted.

## Further Notes

- Builds on the backend-owned Queue and outbound Runner, mid-turn stdin injection verified against the pinned CLI and the Git Proxy with Job tokens.
- The backend side (dispatch, `job.start` composition, Turn handling, recovery, projection) is covered by the Agent sessions work; Worktree layout and the Git Proxy by the Git integration work.
- The real Docker and `claude` scenarios are opt-in and still to run; a production-container smoke check up to the Agent going idle has passed.
