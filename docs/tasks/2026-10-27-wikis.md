# Wikis with a shared Agent conversation and Reset Chat

## Specs

- [Wikis](../specs/wikis.md)
- [Conversation](../specs/conversation.md)
- [Agent sessions](../specs/agent-sessions.md)

## Problem Statement

The team keeps shared knowledge in Git repositories of Markdown files, with their own Claude Skills and conventions for maintaining them. Asking an Agent questions about that knowledge, or asking it to update the docs, today means creating a throwaway Project and Task, which mixes documentation with the Board and gives every question its own isolated conversation. People want one place per knowledge base where anyone can talk to an Agent that follows the repository's own rules, and a way to start over when the conversation gets long or goes stale, without losing the files.

## Solution

A Wiki section on web and mobile lists Wikis. Any User creates a Wiki by choosing a name, an optional description, an Agent and a Repository with its Base Branch. Each Wiki has one conversation shared by every User, with the same Comments, Internal Notes, attachments, streaming output, delivery information and Session controls as a Task. The Agent works in the Repository's Worktree with the repository's instructions and Skills loaded, on its own Task Branch. Users can rename a Wiki, edit its description, change its Agent, reset its chat for everyone (a fresh Agent conversation, files kept) and delete it from the app without touching the remote Repository. Underneath, a Wiki is a Project of kind `wiki` with one backing Task, so it reuses the whole Task runtime.

## User Stories

1. As a User, I want a Wiki section separate from Projects in the web app, so that knowledge bases don't clutter the Board.
2. As a User, I want the same Wiki section in the Flutter app, so that I can use Wikis from my phone.
3. As a User, I want to see every Wiki with its name, description and Repository, ordered by name, so that I can find the right one.
4. As a User, I want to create a Wiki by choosing its name, description, Agent, Repository and Base Branch, so that I can start a shared knowledge base on an existing repository.
5. As a User, I want the Base Branch pre-filled with the Repository's default branch, so that the common case needs no typing.
6. As a User, I want the Repository picker to list the Repositories of every Git Connection and show the errors of connections that fail, so that I know why a repository is missing.
7. As a User, I want a clear error when the Repository, the Base Branch, the Git Connection or the Agent is invalid, with nothing half-created, so that I can fix the input and retry.
8. As a User, I want assigning the Agent at creation to start nothing until someone writes, so that the Agent doesn't spend effort on an empty conversation.
9. As a User, I want to open the new Wiki right after creating it, so that I can ask my first question.
10. As a User, I want one conversation shared by every User, so that the team builds on each other's questions.
11. As a User, I want to see other Users' Comments and the Agent's output live, so that the Wiki feels like a team chat.
12. As a User, I want Internal Notes, attachments and delivery badges in the Wiki conversation, so that it works like any Task conversation.
13. As a User, I want the Agent to follow the repository's CLAUDE.md, Skills and conventions, so that it maintains the Wiki the way the repository defines.
14. As a User, I want the Agent told that the conversation is a shared discussion with several Users and that it must preserve existing documentation and Skills, so that it behaves well in a team setting.
15. As a User, I want the Agent's changes on its own branch and proposed through a pull request, so that edits to the Wiki go through review.
16. As a User, I want to see the Wiki's branch and pull request from the Wiki view, so that I can review the Agent's changes.
17. As a User, I want Stop and Retry on a Wiki like on a Task, so that I control the Agent there too.
18. As a User, I want to rename a Wiki and edit its description, so that it stays accurate.
19. As a User, I want to change a Wiki's Agent, so that a better-suited Agent can take over.
20. As a User, I want to reset the chat for everyone after a confirmation, so that we can start a fresh conversation when the current one is long or stale.
21. As a User, I want a reset to keep the Repository files, the branch and the checkout, so that the knowledge itself is never lost.
22. As a User, I want the next Comment after a reset to start a new Claude conversation that knows nothing of the old messages, so that the reset really starts over.
23. As a User, I want a reset to stop a running Agent and drop queued messages, so that no pre-reset work continues.
24. As a User, I want late output from a cancelled Agent process never to reappear in the cleared chat, even after a reconnect, so that the reset holds.
25. As a User, I want a reset to also forget the conversations of previously assigned Agents, so that reassigning an old Agent doesn't bring old context back.
26. As a User viewing a Wiki, I want the conversation to clear on my screen when someone else resets it, so that I don't act on deleted messages.
27. As a phone user who was offline during a reset, I want the app to notice it on reconnect and discard cached messages, so that my cache matches the server.
28. As an Agent operator, I want a cancelled Agent to stay busy until its process exits, so that an Agent never runs two processes at once.
29. As a User, I want to delete a Wiki from the app while the remote Repository stays, so that I can stop tracking it without losing the files.
30. As a User, I want to follow, unfollow and mute a Wiki, so that I control its notifications.
31. As a phone user, I want notifications for a Wiki to open its Wiki conversation, so that I land in the right place.
32. As an operator, I want Sessions created before Wikis to keep resuming their existing Claude conversations after the upgrade, so that the migration loses no context.

## Implementation Decisions

- A Wiki is stored as a Project with kind `wiki` and one backing Task (number 1). The Projects list returns only Projects of kind `project`. The Wiki API (list, get, create, update, reset, delete) presents the pair as one Wiki: id, name, description, Repository, Agent, backing Task id, created and updated times.
- Creation resolves and checks the Repository (Git Connection, repository access, Base Branch existence, Base Branch Protection) before the transaction, then, under the Git Connection's lock: picks a random free key (`W` plus five letters), creates the Project with default Statuses, sets kind, Repository and fixed Wiki Agent Instructions, creates the backing Task (title and description from the Wiki, priority none, created by the User) and assigns the Agent through the ordinary Task update. All in one transaction.
- Request bodies: name trimmed 1 to 200 characters, description up to 100,000 characters, Agent id required on create and optional on update, Repository only on create. Unknown fields are rejected.
- Update changes the Project's name and description and the backing Task's title, description and Agent through the ordinary Task update (Revisions, reassignment rules).
- A new `wikis` real-time topic carries `wiki.changed` with the Wiki id on create, update, reset and delete.
- Sessions gain an optional Claude session identity; the dispatcher passes it to the Runner, falling back to the Session id. A migration restores the fallback for Sessions that an earlier version of the Wiki migration had filled with random identities.
- Tasks gain a chat generation. Task cards, Task details and Timeline pages carry it; the Timeline page is read in a transaction that locks the Task, so its entries and generation match.
- Jobs gain a discard-output flag. Reset sets it, together with cancellation, on every Job of the backing Task and clears their stored projection, error and setup output. Runner messages of a discarded Job are acknowledged and ignored except its exit or failure, which finishes the Job and frees the Agent. On Runner reconnect the backend repeats the cancellation for a discarded Job; recovery skips the projection, the resume and the System Comment. The Git Proxy refuses discarded Jobs. Comment delivery queues instead of injecting into a discarded Job.
- Reset deletes the backing Task's Queue Entries, Comments (and their blobs after commit), Agent items, Revisions, Timeline positions, Turns and stream events, resets every User's read position to zero, gives every Session a new identity with `started` cleared (`pending` for the current Agent, `paused` for others), bumps the Task version and chat generation, and emits `timeline.reset` on the Task topic.
- Delete reuses Task deletion (refused with 409 while a Job is active, Worktree removal, blob cleanup) and then deletes the Project.
- Web: Wiki sidebar entry, Wiki list and creation dialog, Wiki view with the Task conversation (Revisions hidden), session chip, Stop, Retry, Reset chat, settings and delete; reset clears the cached Timeline and live text.
- Flutter: Wiki section in the rail, Wiki list, creation and settings sheet, Wiki conversation with Reset chat, follow and mute, settings and delete; reset clears the conversation and its cache; chat generation checks on fetch and on loading older pages; notifications for a backing Task open the Wiki.

## Testing Decisions

- Seam 1, backend public API with the fake Runner and fake Git provider (`backend/test/wikis.test.ts`): creation with Repository and Agent, separation from Projects, pending Session until the first Comment, Wiki Agent Instructions in the system prompt; multi-User chat with reset broadcast; new Claude session after reset with the same Worktree and Task Branch and no old context, late output discarded, chat generation incremented; reset of previously assigned Agents; invalid Repository, Base Branch and Agent with nothing left behind, and authentication; queued Comments cleared while the Runner is offline with cancellation on reconnect; deletion.
- Migration upgrade from the originally applied Wiki migration keeps existing Sessions resuming their conversation (`backend/test/migrations.test.ts`).
- Frontend Playwright (`frontend/e2e/wikis.spec.ts`): create a Wiki from the UI, chat from two browsers, reset clears both, reload stays empty.
- Flutter tests (`mobile-app/test/wiki_test.dart`): shared Comments, subscriptions and Session APIs; another User's reset clears live output, pagination and cache; a missed reset detected on refresh; navigation and reset on phone and desktop widths; creation on a phone.

## Acceptance Criteria

- [x] Any signed-in User can create a Wiki with a name, description, Agent, Repository and Base Branch; anonymous requests answer 401.
- [x] Missing or inaccessible Repositories and unknown Agents answer 400 and leave no Wiki, Project or Task.
- [x] Wikis appear in their own section on web and mobile and are excluded from the Projects list.
- [x] The Agent's Session stays pending until the first User Comment, which starts a new `claude` conversation in the Repository's Worktree with the Wiki Agent Instructions.
- [x] Several Users post in the same conversation and see each other's Comments live.
- [x] Users can rename a Wiki, edit its description and change its Agent.
- [x] Reset Chat clears Comments, Agent items, Revisions and stored output for everyone and is broadcast to every connected participant.
- [x] Reset cancels the active Job, clears queued Messages, and rotates the Claude identity of every Session of the Wiki, previously assigned Agents included.
- [x] After a reset the next Comment starts a new conversation without resume, in the same Worktree and Task Branch, with no pre-reset context.
- [x] A cancelled Job keeps its Agent busy until exit, and its late events never repopulate the chat, including after reconnect.
- [x] The Flutter app detects a reset after reconnecting and discards cached conversation pages.
- [x] Deleting a Wiki removes it and its conversation from the app and keeps the remote Repository.
- [x] Existing Sessions keep resuming their Claude conversation after the upgrade.
- [ ] The web Wiki view offers every Task Session control, Notify agent included (the web Wiki view has Stop and Retry but no Notify agent banner).

## Out of Scope

- Changing a Wiki's Repository or Base Branch after creation.
- Browsing or editing the Wiki's Markdown files in the app.
- Several conversations per Wiki.
- Deleting the remote Repository or the Task Branch.
